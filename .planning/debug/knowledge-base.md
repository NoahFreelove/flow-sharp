## chord-dynamic-bar-doubling — dynamic+chord note-stream bar renders at ~2x duration
- **Date:** 2026-06-25
- **Error patterns:** note stream, dynamic marking, chord, IsChordTone, InterpolateVelocities, MusicalNoteData reconstruction, bar doubling, beat cursor, ToTimeline, velocity interpolation, drunk pianist drift, midi2flow
- **Root cause:** `NoteStreamCompiler.InterpolateVelocities` rebuilt each interpolated middle note with the 12-arg `MusicalNoteData` positional constructor, silently resetting the 5 trailing fields (IsChordTone, DurationFraction, OnsetOffset, DurationOverlap, PortamentoMs) to defaults. Dropping IsChordTone made interpolated chord tones advance the bar's beat cursor in `BarType.ToTimeline` instead of sharing the lead onset, so any bar mixing a dynamic (≥2 distinct velocities → interpolation runs) with chords overran (doubled).
- **Fix:** Rebuild via `notes[i].With(velocity: vel)` instead of the positional ctor — overrides only velocity and passes every other field through by null-coalesce, preserving IsChordTone. One edit covers both call sites (main note-stream path + per-voice CompileVoiceBlock).
- **Files changed:** flow-lang/Runtime/NoteStreamCompiler.cs, flow-lang.Tests/Integration/Debug2026/ChordDynamicBarDoublingTests.cs
- **Bug class / lesson:** Any per-bar `MusicalNoteData` reconstruction MUST use `MusicalNoteData.With(...)` rather than the positional constructor, to avoid silently dropping IsChordTone / DurationFraction / OnsetOffset / DurationOverlap / PortamentoMs. The 2026-06-09 transform audit fixed this drop-on-reconstruct pattern elsewhere (NoteType.cs With() docs) but missed `InterpolateVelocities`. When auditing for this pattern, grep for `new MusicalNoteData(` outside the With() builder itself.

## varispeed-aliasing-static (FALSIFIED LEAD — do NOT re-attempt AA resampler for this) — per-beat "static" on sampled-piano renders
- **Date:** 2026-06-26
- **Error patterns:** sampled piano, varispeed, resample, aliasing, decimation, per-beat static, crackle, grit, high register, ragtime, VarispeedResample, linear interpolation, SampleCache, GetVarispeed, onset transient
- **Status:** RESOLVED 2026-06-26 (commit 487f248 on dev). User confirmed by ear: per-beat static GONE, piano intact. Full suite green except 2 pre-existing flow-midi RH/LH-split failures (unrelated — flow-midi has no audio dependency).
- **Bug class / lesson:** A sampled-instrument render path that appends an exponential release TAIL after the authored window MUST make the ADSR envelope meet that tail CONTINUOUSLY at the boundary frame. Two ways the seam opens: (1) a non-zero ADSR release ramps the envelope toward 0 at the authored end while the tail restarts at level=1.0 on the raw sample → full-amplitude step; (2) a rescale path (short notes, requestedADR>totalFrames) dumps floor-rounding leftover frames into the release ramp even when release==0 → a 1-3 frame dip. Fix posture: on the sampled path set baseRelease=0 (the tail IS the release) and route rescale leftover to SUSTAIN when release==0; keep release>0 paths (synth/SFZ/drum) byte-identical. Discriminator that found it: read the 2nd-difference (curvature) at the largest transients to separate true single-sample discontinuities (clicks) from loud-passage slew (music), and verify with controlled isolation (single note + chord clean; only the DENSE SHORT-note mix shows the steps).
- **Actual root cause (CONFIRMED, NOT aliasing):** envelope/tail boundary discontinuity in the SAMPLED render path. `SampledInstrumentRenderer.Render` applied the ADSR envelope (baseRelease=0.05) over [0, authoredFrames) — ramping the signal to ~0 at the authored end — then the exponential release-tail loop restarted at level=1.0 on the RAW sample → a step back to full amplitude. Compounded by `EnvelopeProcessor.GenerateADSRCurve`'s rescale path dumping its floor-rounding leftover into the release ramp even when release==0 (short notes). Step size = raw sample amplitude at the authored-end frame → large for SHORT notes, beat-aligned, summing into per-beat "static". Fix: baseRelease=0 on the sampled path + route rescale leftover to SUSTAIN when release==0 (synth/SFZ/drum paths with release>0 stay byte-identical). Measured: ragtime max|2nd-diff| 0.0709→0.0112, click events (|2nd-diff|>0.03) 198→0; two-run cmp-clean preserved. 5 sampled-instrument baselines (piano/flute/brass) legitimately shift and need re-recording.
- **Lesson — controlled isolation beat the metric trap twice:** isolated single notes AND loud chords were clean; only the DENSE SHORT-note multi-track mix showed the steps. The discriminating moves were (a) a voice-pool sweep (8/32/256 → byte-identical) to falsify voice-stealing, and (b) dumping the raw waveform around the largest transients to SEE step-vs-slope, then reading 2nd-difference (curvature) rather than 1st-difference to separate true discontinuities (clicks) from loud-passage slew (music).
- **FALSIFIED hypothesis:** "Per-beat static is decimation aliasing in `FileIO.VarispeedResample` (linear interp, no anti-aliasing lowpass) on upshift (ratio>1)." DISPROVEN by three independent measurements: (1) a CORRECT band-limited windowed-sinc anti-aliased resampler changes the real `renderSong s "piano" 0.4s` ragtime by only **-61.7 dB** (inaudible); (2) the C6 piano sample has ~100x less energy above 6 kHz than below, so a ratio-2 upshift has almost nothing to fold back; (3) the "hf-roughness scales with pitch C4=0.009→C7=0.078 (~9x)" evidence is a **metric artifact** — the ORGAN (pure synthesis, aliasing physically impossible) climbs the same mean-|2nd-difference|/RMS metric FASTER (C4=0.014→C7=0.547) because the metric scales ~frequency². Ragtime RH is mostly octave-5 (small shifts, many DOWNshifts which the fix never touches).
- **Do NOT re-attempt:** Do NOT re-derive a varispeed anti-aliasing resampler to fix THIS per-beat static. The AA resampler (`VarispeedResampleAntiAliased`: Blackman-windowed sinc, lobes=16, cutoff=1/ratio, ratio≤1 delegates to linear; Option-B scoping = sampled-instrument callers only, loadWav untouched) is **correct and unit-tested (5/5) and revivable** — but ONLY worth shipping if extreme-upshift sample quality ever becomes a goal. It was REVERTED 2026-06-26 (uncommitted, blast radius zero) because it does not fix the audible bug.
- **Lesson — metric confound:** "HF roughness / mean-|2nd-difference| per RMS rises with pitch" is NOT evidence of aliasing; it rises with pitch for ANY signal because the difference operator is a ~freq² high-pass. Always run the metric against a control that CANNOT exhibit the suspected defect (here: organ = no resampling). If the control shows the same trend, the metric is confounded.
- **Also falsified (intermediate pivot, kept for the record):** beat-aligned note-ONSET-transient summing (chords, non-zero first-frame DC) and tail-end truncation and voice-stealing were ALL falsified by controlled experiment — isolated single notes AND loud chords end clean (-78 dBFS, zero |1st-diff|>0.02); a voice-pool sweep (8/32/256) produced byte-identical output. Only the DENSE SHORT-note multi-track mix exposed the steps → the discriminator was the SHORT authored window landing the envelope/tail boundary jump while the sample is still loud (the real cause above), not onsets.
- **Out-of-scope follow-up (NOT fixed; deliberate):** Staccato/Marcato use sustain=0, so on the sampled path their envelope ends at 0 and they keep a pre-existing boundary seam where the tail restarts at level=1.0. This is a SEPARATE articulation-dependent-tail decision — closing it cleanly would change the `SampledArticulationTailWindowTests` contract. Not present in the ragtime material; tracked as a distinct future item. The shipped fix only makes sustained (sustain>0) notes continuous.

## playground-every-other-run-silence — WASM playground: audio alternates audible/silent on repeated runs of the same snippet
- **Date:** 2026-06-26
- **Error patterns:** WASM playground, every-other-run silence, alternating audio, intermittent silence, AudioContext closed, suspended context, source.start silent, WebAudioBackend.Dispose, closeContext, ctx.close, _audioContext null, NewEngineForRun, per-run engine recycle, FlowEngine.Dispose, AudioPlaybackManager.Dispose, D-48-08, one context per tab, gesture frame, resumeAudio, flow-runtime.js, Phase 48 frozen runtime
- **Status:** RESOLVED 2026-06-26 (commit 0c3073e on dev). Root cause CONFIRMED in-browser (NOT trusted on code trace alone — prior session's "confirmed" lead had been falsified by measurement). User confirmed by ear: organ hymn audible on every run, 4-5× in a row; alternating silence gone.
- **Root cause (CONFIRMED, lifecycle chain):** `WasmEntry.NewEngineForRun` disposes the previous `FlowEngine` on EVERY `RunFromJs` (the fresh-engine-per-run reset that fixes "Variable already declared" on a second run). `FlowEngine.Dispose → AudioPlaybackManager.Dispose → WebAudioBackend.Dispose → JS closeContext`, and `closeContext` called `ctx.close()` + nulled the module-global `_audioContext`. But `_audioContext` is a ONE-PER-TAB singleton (D-48-08). So Run N's gesture-frame `resumeAudio()` resumed the shared context; then RunFromJs disposed engine(N-1) → `closeContext` tore the shared context down mid-run; then engine(N)'s `(play)` → `createAudioContext` returned the now-CLOSED context (or recreated a SUSPENDED one outside the gesture) → `source.start()` silent. Run 1 escaped (no prior engine to dispose). The async close racing the synchronous play made the parity timing-dependent → the every-other-run alternation.
- **In-browser confirmation:** playwright `/playground?e2e=1` exposes `window.__flowAudioCtx.state`. BEFORE fix across 5 Run clicks: `running, closed, running, closed, running` (perfect alternation); temporary `[DBG]` logs showed `closeContext` firing between `resumeAudio` and that run's `createAudioContext` on exactly the silent runs (2 & 4). AFTER fix: `running ×5` (instrumented and final un-instrumented run).
- **Fix:** Candidate A (JS-only, no WASM rebuild). `closeContext` now drains `_activeSources` (stops active sources) but does NOT call `ctx.close()` and does NOT null `_audioContext` — the tab-lifetime context persists (resumed/suspended) and is GC'd on tab close. Applied byte-identically to the published copy AND the canonical source.
- **Files changed:** flow-site/static/wasm/flow-runtime.js (served + committed copy), flow-lang/wasm/flow-runtime.js (canonical — kept byte-identical so a future sync-runtime.sh republish won't regress it).
- **Bug class / lesson:** In the WASM runtime, a per-run resource recycle (`NewEngineForRun` disposing the prior `FlowEngine`) MUST NOT tear down process/tab-lifetime singletons. The AudioContext is one-per-tab (D-48-08) — its lifetime is decoupled from per-run engine `Dispose`; only stop active sources on recycle, never `close()` the context. When a Dispose chain reaches a module-global singleton shared across runs, audit whether Dispose is firing per-run vs. once at real teardown. Also: even a DIRECT lifecycle chain (dispose→close→null) was confirmed by in-browser observation before committing — the prior varispeed-aliasing session taught that a plausible "confirmed" cause can be falsified by measurement.
- **Out-of-scope follow-up (optional v1.6 hardening, NOT done):** Candidate B — decouple the AudioContext from the per-run engine in C# (route script `(play)` through the process-shared `WasmEntry._sharedBackend`, and/or make `WebAudioBackend.Dispose` close the context only on real `DisposeFromJs`, not per-run recycle). Requires `dotnet publish -p:FlowTarget=Web` + `bash flow-site/scripts/sync-runtime.sh`. The canonical flow-runtime.js already carries Candidate A, so a republish won't regress the fix in the meantime.
