# Quick Task 260611-wp2 — Note-stream cutoff fix

## Problem (confirmed natively)

A note stream like `| C4q D4q E4q F4q G4q A4q B4q C5h |` (9 beats of content) compiles
to ONE overfull 4/4 bar. `SequenceData` computes that bar's length as the time-signature
**numerator (4)** rather than its **actual content (9 beats)**, so:

- `(str sequence)` reports `Sequence[1 bars, 4 beats total]` (should be 9).
- `PlaybackFunctions.MixVoicesToBuffer` sizes the mix buffer to 4 beats → only the first
  4 quarter notes render. Rendered WAV = 2.000s instead of 4.5s.
- Chord stream `| [D4 F4 A4]h [G3 B3 D4]h [C4 E4 G4]w |` (8 beats) truncates to the
  first 2 chords (4 beats).

This is the live-playground "note streams cut off after ~1 bar" bug. Present in HEAD and
in the frozen WASM bundle.

## Root cause

`flow-lang/TypeSystem/SpecialTypes/SequenceType.cs`:
- `AddBar` (line 40): `TotalBeats += bar.IsPickup ? bar.GetActualBeats() : bar.TimeSignature.Numerator;`
- `ToTimeline` (line 56): same ternary for per-bar offset.

A non-pickup bar always contributes `Numerator` beats regardless of actual note content.

## Fix (charitable, minimal-regression)

For non-pickup bars use `Math.Max(bar.TimeSignature.Numerator, bar.GetActualBeats())` in
BOTH `AddBar` and `ToTimeline`:

- Overfull bar (9 beats in 4/4) → `max(4, 9) = 9` — fixes the cutoff.
- Exact bar (4 beats) → `max(4, 4) = 4` — unchanged.
- Underfull bar (1 beat) → `max(4, 1) = 4` — still pads to the full bar, preserving
  existing multi-bar layout + two-run determinism baselines.
- Pickup bars stay `GetActualBeats()`.

`GetActualBeats()` already excludes chord-tones (so a chord counts once by its lead tone),
so the chord case resolves to 8 beats correctly.
