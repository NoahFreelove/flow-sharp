Output: One edited file (`flow-lang/Runtime/ExecutionContext.cs`) carrying the cache field + `InvalidateMusicalContextCache()` helper + cache wiring across all six mutation entry points + a SUMMARY.md documenting the FULL CACHE PATH choice with bench numbers.

Grep results — every site that mutates state observable by GetMusicalContext():

**A. Frame stack mutations** (change which frames are walked):
1. `ExecutionContext.PushFrame()` — line 390. Pushes a new StackFrame whose MusicalContext is null initially. **MUST invalidate** (new top frame changes the walk).
2. `ExecutionContext.PopFrame()` — line 403. Pops the top frame. **MUST invalidate**.

**B. Per-frame MusicalContext assignment** (changes a frame's MusicalContext from null → non-null OR replaces it):
3. `Interpreter.ExecuteMusicalContext` line 335 — `_context.CurrentFrame.MusicalContext = musicalCtx;`. This is the ONE external site that writes `.MusicalContext = …` on a frame already in the live call stack. PushFrame at line 163 invalidates first, but the cache could be re-populated by some intermediate read between PushFrame and this assignment (`_context.GetMusicalContext().Tempo ?? 120.0` at lines 230 + 240 for Rit/Accel branches). **MUST invalidate at the assignment** to be safe.
4. `ExecutionContext.RestoreState` line 828 — `GlobalFrame.MusicalContext = snap.GlobalFrameMusicalContext;` inside hermetic-test restore. **MUST invalidate**.

**C. Field-level mutations on a live frame's MusicalContext** (mutate fields the cache already aliases — most subtle case):
   - All field writes on `musicalCtx` in `ExecuteMusicalContext` (lines 177/197/211/220/231/241/257/273/284/301/310/324) happen BEFORE the frame's `.MusicalContext` is assigned on line 335. So these mutations happen on a local-variable instance not yet visible to GetMusicalContext. **No invalidation needed for these — covered by site #3 above.**
   - **There are NO sites that mutate the field of an already-assigned frame.MusicalContext.** Confirmed by grep `MusicalContext\.(Tempo|TimeSignature|Swing|Key|Velocity|Pan|Gain|ReverbTime|VoicePoolSize|SustainPedal|Tuning)\s*=` — zero matches outside the local-variable construction in ExecuteMusicalContext.

**D. TuningStack mutations** (modify the Stack<RenderTuning> on a live frame's MusicalContext — the cache shares this stack by reference per the comment at ExecutionContext.cs:506-510):
5. `ExecutionContext.SetFileScopeTuning` line 617 — pops + pushes on `GlobalFrame.MusicalContext.TuningStack`. **MUST invalidate**.
6. `ExecutionContext.PushTuning` line 634 — pushes on `CurrentFrame.MusicalContext.TuningStack`. **MUST invalidate**.
7. `ExecutionContext.PopTuning` line 647 — pops `CurrentFrame.MusicalContext.TuningStack`. **MUST invalidate**.
8. `ExecutionContext.ResetBlockTuningStack` line 665 — pops down to ≤ 1 on `GlobalFrame.MusicalContext.TuningStack`. **MUST invalidate**.
9. `ExecutionContext.SetTuning` line 587 — `[Obsolete]` shim that delegates to `SetFileScopeTuning`. Invalidation cascades through #5. **NO direct work needed**.

**Note on the `MusicalContext.TuningStack` reference-share** (ExecutionContext.cs lines 506-510, comment "Reference-share the stack — readers consume ActiveTuning (peek), not the stack instance, so aliasing is safe + cheaper than cloning"): this is the load-bearing reason invalidation MUST fire on PushTuning/PopTuning/SetFileScopeTuning/ResetBlockTuningStack. The cached `resolved` instance's `.TuningStack` field is THE SAME REFERENCE as some frame's `.TuningStack` (the first frame walked that had a non-empty TuningStack). Any push/pop on the underlying frame's stack would be visible through the cached resolved instance — but since we invalidate, the next call gets a fresh resolution and a fresh aliasing.

**Caller-mutation audit** (whether any caller MUTATES the returned MusicalContext):
   - Grep `GetMusicalContext()` produces 30 hits. Every single one reads a property (`.Tempo`, `.TimeSignature`, `.Key`, `.Velocity`, `.Pan`, `.Gain`, `.ReverbTime`, `.ActiveTuning`, `.SustainPedal`, `.VoicePoolSize`) or calls `.Clone()`. **Zero callers mutate.** The read-only contract holds.
   - The HIGHEST-RISK caller pattern is `SongFunctions.cs:36` (`new SectionData(name, sequences, context.GetMusicalContext())`) — SectionData STORES the reference long-term. But SectionData consumers (`SongRenderer.cs:266-292/500-510/641`, `MidiExport.cs:331-340/389-390`, `MusicXmlExport.cs:148-151`, `LilyPondExport.cs:131`) ONLY read fields. They never write. Confirmed by `grep -rn "section\.Context\." --include="*.cs"`.
   - The hermetic-test pattern at `ReverbTimeContextTests.cs:47/55` already calls `.Clone()` on the returned value — they explicitly want independent snapshots, which is compatible with our shared-cache return.

**Audit verdict:** FULL CACHE PATH is SAFE. No defensive `.Clone()` needed at the cache return boundary. Wire 5 invalidation entry points (PushFrame, PopFrame, SetFileScopeTuning, PushTuning, PopTuning, ResetBlockTuningStack — that's 6, since SetTuning's `[Obsolete]` shim is a no-op) plus 2 direct-write sites (Interpreter.cs:335 and ExecutionContext.cs:828). The Interpreter.cs:335 invalidation requires a small helper because Interpreter writes `CurrentFrame.MusicalContext = X` directly — we need a setter on ExecutionContext or invalidate inline at the assignment site. See Task 2 Decision for the chosen approach.
