# QUICK-260504-w24: Decibel/Beat numeric compat hot fix — Summary

Composers now type the natural musical literal `(gain rendered -12dB)` and hit
the existing dB-interpreting code path instead of getting `"No matching
overload for function 'gain' with argument types (Buffer, Decibel)"`. Two
music-domain numeric types (Decibel, Beat) gained the
`IsCompatibleWith(Double|Float)` override that CentType already provides; the
`gain` builtin gained an explicit `(Buffer, Decibel)` overload registration
delegating to the same lambda.

## What changed

### `flow-lang/TypeSystem/SpecialTypes/DecibelType.cs`
- Added `using FlowLang.TypeSystem.PrimitiveTypes;`.
- Added `IsCompatibleWith` override returning true for `DoubleType` and
  `FloatType`, falling through to `base.IsCompatibleWith(target)` otherwise.
- Mirrors CentType.cs:24-27 byte-for-byte; doc comment explains the
  ergonomics intent (avoid "No matching overload" on `(gain buf -12dB)`).

### `flow-lang/TypeSystem/SpecialTypes/BeatType.cs`
- Added `using FlowLang.TypeSystem.PrimitiveTypes;`.
- Added the same `IsCompatibleWith` override; doc comment notes Beat is
  stored as a fractional double (`Value.Beat(double)` in
  `Runtime/Value.cs:41`) so the compat is semantically free.

### `flow-lang/StandardLibrary/Audio/EffectsFunctions.cs:RegisterGain`
- Added a second `registry.Register("gain", gainDecibelSig, GainEffect)` call
  with signature `[BufferType.Instance, DecibelType.Instance]`, pointing at
  the same `GainEffect` lambda. The lambda's `args[1].As<double>()` works
  unchanged because both `Value.Double` and `Value.Decibel` carry a `double`
  in `.Data`.
- Reasoning preserved in the in-source comment: exact-match score (1000)
  beats the compat path's score (500); future-proofs against any later
  `gain(Buffer, Float)` or `gain(Buffer, linear)` addition that would
  otherwise become ambiguous; gives discoverability parity with
  `transpose(Sequence, Cent)` (TransformFunctions.cs:257-260).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocker] Plan's `(sine 220.0 0.05 44100)` is not a registered builtin**
- **Found during:** Test authoring (Step 1, RED).
- **Issue:** The plan's example engine-eval source uses `(sine 220.0 0.05 44100)`, but no top-level `sine` builtin exists. `sine` only appears as a string-keyed synth selector in `NoteSynthesizer.cs:236` and `PlaybackFunctions.cs:124`, plus a docs entry in `BuiltInDocs.cs:90` that doesn't correspond to a registered signature. Buffer construction in Flow goes via `createSineTone(Double duration, Double frequency, Double amplitude)` from `audio.flow:290`.
- **Fix:** Replaced `(sine 220.0 0.05 44100)` with `(createSineTone 0.05 220.0 0.5)` in facts 5 and 6.
- **Files modified:** `flow-lang.Tests/Unit/QuickFixes/DecibelBeatNumericCompatFacts.cs`
- **Commit:** `30102f3` (RED — adapted at authoring time)

**2. [Rule 3 — Blocker] Fact 7 cannot use `Beat b = 1.5` source-level setup**
- **Found during:** Test design.
- **Issue:** The plan's fact 7 uses `Beat b = 1.5` to materialize a Beat value in source, but Flow has no `Beat` literal in the lexer (unlike Cent's `+50c` and Decibel's `+6dB`) and no Beat-producing builtin. `Double 1.5 -> Beat` would require `DoubleType.IsCompatibleWith(BeatType)` or `DoubleType.CanConvertTo(BeatType)`, both of which are out of scope (would be a wider change in the wrong direction). The only Flow-level path to a Beat value today is default-init (`BeatType => Value.Beat(0.0)` at `Interpreter.cs:533`).
- **Fix:** Reframed fact 7 as a generic `FunctionSignature.Matches` assertion at the type-system level: a synthetic `takesDouble(Double)` signature must match `[BeatType.Instance]` after the fix. This is **stronger** than the source-level test would have been because it covers every Double parameter slot in the language (builtins, user procs, lambdas) without depending on a specific source-level setup. Documented the reframing in the test's XML doc comment.
- **Files modified:** `flow-lang.Tests/Unit/QuickFixes/DecibelBeatNumericCompatFacts.cs`
- **Commit:** `30102f3` (RED — adapted at authoring time)

**3. [Rule 3 — Blocker] Lexer ambiguity: `(gain src -12.0)` parses as `(gain (src - 12.0))`**
- **Found during:** Initial GREEN run (fact 5 still failed with `Cannot apply operator Subtract to Buffer and Double`).
- **Issue:** When a `-` follows a Buffer-typed identifier in argument position, the lexer/parser treats it as binary subtraction rather than a leading sign on the next number. The Decibel literal `-12dB` does NOT have this issue because the `dB` suffix forces a single `DecibelLiteral` token (SimpleLexer.cs:400) regardless of leading sign — which is exactly the ergonomics win this fix delivers. The plain Double literal `-12.0` has no such suffix, so the sign binds infix.
- **Fix:** Bound `-12.0` to a variable (`Double minus12 = -12.0`) and passed `minus12` as the gain argument, dodging the parse-time ambiguity. The fact still tests what it must: that the dB literal and an equivalent Double value produce per-sample identical output through the existing GainEffect lambda. In-source comment in the test explains the disambiguation.
- **Files modified:** `flow-lang.Tests/Unit/QuickFixes/DecibelBeatNumericCompatFacts.cs`
- **Commit:** `1960a92` (GREEN — folded into the same commit as the fix because the fact's correctness is tied to the GREEN state)

None of the deviations changed the scope, the goal, or the surface of the fix. They were authoring corrections to make the facts express the intended assertions against the actual codebase shape.
