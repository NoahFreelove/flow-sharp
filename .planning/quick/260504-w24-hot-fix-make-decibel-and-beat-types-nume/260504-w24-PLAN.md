<objective>
Hot fix to unblock the user who literally just typed `(gain rendered -12dB)` and got `error: No matching overload for function 'gain' with argument types (Buffer, Decibel)`. Two of the music-domain numeric types (Decibel and Beat) lack the `IsCompatibleWith(DoubleType or FloatType)` override that CentType already provides, so they bounce off any builtin signature that takes a `Double` — including the pre-existing `gain(Buffer, Double)` overload that already interprets its second argument as dB.

Purpose: this is the "ergonomics first / easy cases fast" rule from CLAUDE.md and the project's "no type strictness for its own sake" non-goal applied directly. A composer typing the natural musical literal (`-12dB`) for a function that already documents its parameter as decibels should not be told "no matching overload". The fix is the smallest possible change that mirrors a working precedent (CentType).

Output: two two-line additions to type files (Decibel + Beat IsCompatibleWith), one explicit overload registration line in EffectsFunctions.cs (delegates to the existing lambda — provides exact-match score and discoverability parity with transpose(Sequence, Cent)), and one xUnit Facts file with both type-system-level facts and engine-eval facts that exercise the fix end to end.

Out of scope (deferred to Phase 26.2 per orchestrator constraint): MillisecondType, SecondType, SemitoneType compat changes; delay/compress/sidechain Decibel overloads; gain dB-vs-linear semantic policy; HertzType.
</objective>
