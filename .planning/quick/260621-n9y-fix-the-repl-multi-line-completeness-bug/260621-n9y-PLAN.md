<objective>
Fix the REPL multi-line completeness bug. `ReplInputCompleteness.IsInputComplete`
(flow-interpreter/ReplLineEditor.cs:606) uses a `pipeCount % 2 == 0` parity heuristic
to decide whether a note stream is terminated. That heuristic is wrong: the lexer emits
one `TokenType.Pipe` per `|` INCLUDING bar separators, so a single-line N-bar stream
`| bar1 | bar2 | ... | barN |` has N+1 pipes. Even-bar-count streams (e.g. the reported
4-bar freeze = 5 pipes) are judged "incomplete" → the REPL hangs forever in continuation
mode. It also false-positives the other way (`| C4 | D4` has 2 pipes = even → wrongly
judged "complete").

Replace the parity term with a note-stream-aware scan that mirrors the parser's
`IsEndOfNoteStream()` lookahead (Parser.NoteStream.cs:556): track an `inStream` boolean;
a pipe seen while not in a stream OPENS it, a pipe seen while in a stream is a closing
pipe UNLESS the next token can continue a note stream (then it is a bar separator). The
input is incomplete iff `inStream` is still true at end of buffer.

Purpose: composers can paste / type multi-bar note streams in the REPL without it
freezing — the core "hear it immediately" value depends on the REPL accepting valid input.
Output: corrected `IsInputComplete` + regression tests.
</objective>

  <action>
In `ReplInputCompleteness.IsInputComplete` (flow-interpreter/ReplLineEditor.cs:606),
preserve VERBATIM: the empty/whitespace early-return, the backslash-at-EOL early-return,
the `internal proc` early-return, the SimpleLexer tokenization, and the
`blockDepth`/`procDepth`/`parenDepth`/`bracketDepth` counters and their `<= 0` final
checks. ONLY replace the pipe handling.

Remove the `int pipeCount = 0;` declaration, the `else if (token.Type == TokenType.Pipe) pipeCount++;`
arm (including its sweep-0614 comment), and the `&& (pipeCount % 2 == 0)` term in the
return expression.

In their place, add a note-stream-aware scan that tracks a `bool inStream = false`.
Because the existing loop is a single `foreach (var token in tokens)` and the continuation
decision needs the NEXT token, index the token list instead: iterate
`for (int i = 0; i < tokens.Count; i++)` over the already-materialized `tokens` list,
referencing `tokens[i]` for the brace/proc/paren/bracket counting (keep that logic
identical, just sourced from `tokens[i]`). Add the pipe handling as a new arm:

  - When `tokens[i].Type == TokenType.Pipe`:
    - If NOT `inStream`: this pipe OPENS a stream → `inStream = true;`
    - Else (already `inStream`): peek the next token `tokens[i + 1]` if it exists. If the
      next token can continue a note stream (predicate below), this pipe is a bar
      separator → stay `inStream` (no change). Otherwise it is the closing pipe →
      `inStream = false;`. If there is NO next token (pipe is the very last token), it is
      ambiguous mid-typing → treat as still open: leave `inStream = true` (do NOT close).

Add a private static helper `ContinuesNoteStream(Token next)` returning bool, mirroring the
INVERSE of Parser.NoteStream.IsEndOfNoteStream() (a token AFTER a pipe means the stream
continues). Return true for these token types: `TokenType.NoteLiteral`, `TokenType.Underscore`,
`TokenType.LBracket`, `TokenType.Pipe` (adjacent pipe = multi-line next-bar opener),
`TokenType.ChordLiteral`, `TokenType.LParen`, `TokenType.GreaterThan`, `TokenType.LBrace`.
Also return true when the token is `TokenType.Identifier` AND any of:
(a) `FlowLang.StandardLibrary.Harmony.ScaleDatabase.IsRomanNumeral(next.Text)` — keep this
one faithfully so roman-numeral streams (`| I IV V |`) are not early-submitted;
(b) the text is an articulation mark: `next.Text is "stacc" or "ten" or "marc" or "leg" or "cresc" or "decresc"`;
(c) the text is a duration letter: `next.Text is "w" or "h" or "q" or "e" or "s" or "t"`;
(d) the text is a lowercase-initial identifier (variable ref):
`next.Text.Length > 0 && char.IsLower(next.Text[0])` AND it is NOT one of the duration
letters already covered (those are covered by (c) — keeping the `&& not duration` exclusion
faithful to the parser, though harmless either way since both return true). Otherwise return false.

NOTE: `TryParseDynamicMarking` from the parser is parser-private. Omitting the dynamic-marking
branch is acceptable per the constraint — but the duration-letter set (c) already covers the
single-letter dynamics overlap minimally, and lowercase-identifier (d) already covers `p`/`mp`/`mf`/`f`/`ff`
etc. as lowercase variable-shaped tokens, so common dynamic-marked streams still continue. Do
NOT add a parser-private dependency.

Reference the helper in the new pipe arm. Add the
`using FlowLang.StandardLibrary.Harmony;` directive at the top of ReplLineEditor.cs
(the file already has `using FlowLang.StandardLibrary;` but NOT the `.Harmony` sub-namespace).

Change the final return to:
`return blockDepth <= 0 && procDepth <= 0 && parenDepth <= 0 && bracketDepth <= 0 && !inStream;`

Replace the stale sweep-0614 comment block on the old pipe arm AND the trailing comment on
the return statement with an explanatory comment: note that the parity check was WRONG
because an N-bar single-line stream emits N+1 pipes (a 4-bar stream = 5 pipes = odd =
wrongly "incomplete" → REPL freeze), and that this scan mirrors
`Parser.NoteStream.IsEndOfNoteStream()`: a pipe closes the stream only when the next token
cannot continue it; at end of buffer a still-open `inStream` means the composer is
mid-stream → request continuation. Keep CLAUDE.md C# conventions (file-scoped namespace
already in use here is bracketed-namespace — match the EXISTING brace style of this file;
do not convert it).
