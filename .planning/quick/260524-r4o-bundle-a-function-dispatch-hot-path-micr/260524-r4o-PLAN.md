  <action>
Modify `GetFunctionOverloads(string name)` (currently lines 133-146) to add a fast path that avoids the per-call `new List<FunctionOverload>()` allocation when the overloads live entirely in `this` frame.

Algorithm:
1. `if (_functions.TryGetValue(name, out var localOverloads))` — local hit.
2.   Walk `Parent` via the existing `HasFunction(name)` probe. If `Parent == null || !Parent.HasFunction(name)`, return `localOverloads` directly (treat as read-only — see contract note below). Per the existing StackFrame.HasFunction implementation (line 148-151), the probe is a cheap parent-chain ContainsKey walk that allocates nothing.
3.   Otherwise (parent chain ALSO has overloads for `name` — multi-frame shadow): fall through to the existing allocate-merge path.
4. `else` (no local hit): if `Parent == null` return `new List<FunctionOverload>(0)` (empty); otherwise return `Parent.GetFunctionOverloads(name)` directly (no wrapping). When parent returns its own fast-path local list, that list flows through unchanged — still safe because all 5 known callers are read-only.

Add an XML-doc-comment paragraph above `GetFunctionOverloads` documenting the read-only contract:

  "The returned list MUST be treated as read-only by callers. When only one frame in the parent chain holds overloads for this name, this method returns a direct reference to that frame's internal list to avoid per-call allocation. Mutating the returned list is undefined behavior — register new overloads via DeclareFunction. All 5 in-tree callers (StackFrame self-recursion, ModuleLoader, ExpressionEvaluator, ExecutionContext.ResolveFunction, ExecutionContext.TryResolveFunction) are read-only as of Bundle A (260524-r4o)."
