<objective>
Add two NEW additive overloads to the `renderSong` builtin so composers can pass a
Symbol instrument name (`(renderSong song #piano)`) in addition to the existing
String form (`(renderSong song "piano")`). The Symbol overloads unwrap the symbol's
interned name to a String and delegate to the EXISTING render methods, so output is
byte-identical to the String path.

Purpose: Ergonomic parity — composers already use `#piano`-style symbols for
instrument identity elsewhere (e.g. `(loadSfz #violin)`, the `@sfz` GM dict). Letting
`renderSong` accept the same symbol form removes a String/Symbol friction point.

Output: Two new `FunctionSignature` registrations + thin delegating handlers in
SongRenderer.cs, plus the two matching `internal proc` declarations in audio.flow that
make them reachable from `.flow` source.

Scope guardrails (LOCKED — do not exceed):
- renderSong ONLY. Do NOT touch `play`/`writeWav` auto-routing, sequence-name GM routing
  (`InstrumentRouting.ResolveGmProgram`), or custom-wavetable registration.
- ADDITIVE — the existing `renderSong(Song, String)`, `renderSong(Song, String, Second)`,
  and `renderSong(Song, Function)` overloads stay UNCHANGED. No existing call site
  (90+ across tests/ and examples/) may break.
- `sampler:NAME` stays a string concept. No symbol form for the sampler compound — the
  symbol overload just unwraps to a string and delegates, so a symbol whose interned
  name happens to be `"sampler:..."` would still flow through the existing string
  dispatch, but no new sampler API is added.
- NO worktree isolation for execution (this repo has handed out stale bases). Execute on
  the main tree.
</objective>
