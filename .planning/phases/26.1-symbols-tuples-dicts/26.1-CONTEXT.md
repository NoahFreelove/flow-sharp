# Phase 26.1 — Context

<domain>
## Phase Boundary

Three tightly-coupled language additions land together as Phase 26.1:

1. **Symbol primitive type** — `#foo` literal syntax; interned (pointer-equality); registered as a `FlowType` in `TypeSystem/PrimitiveTypes/` (or `SpecialTypes/` — researcher decides).
2. **Tuple type** — `<<a, b, c>>` literal with per-position types and arity (`<<>>` empty + `<<x>>` singleton are valid); type annotation `<<Note, Beat>>` mirrors literal; `tup@0`/`@1` indexing (same `@N` syntax as array indexing — charitable per memory); `<<a, b>> = expr` destructuring assignment; immutable; structural equality.
3. **Generic `Dict<K, V>`** — Java-generic notation; allowed key types: Int, Long, Float, String, Symbol, Note, Chord, Tuple-of-hashables; constructed via `(dict K V K V ...)` flat or `(dictTuple <<K,V>> <<K,V>> ...)` tuple-pair builtins; **no literal syntax** (preserves S-expr style and avoids `{...}` collision with Phase 19 tuplets); immutable — all mutations return new dicts.

**Foundational dependency:** Phase 26 (prefix-only arithmetic). The new builtins inherit the no-infix philosophy.

**Out of scope** (deferred to later phases): block-scope pragmas, Hertz type, dict literal syntax, lambda parameter destructuring.

</domain>

<decisions>
## Implementation Decisions (locked in this discussion)

### REQUIREMENTS vs ROADMAP reconciliation

**ROADMAP.md (newer) structural spec wins on every divergence with REQUIREMENTS.md (older).** Specifically:

- **Type signature:** `Dict<K, V>` (two type params). REQUIREMENTS' single-param `Dict[T]` is OBSOLETE.
- **Key types:** Int / Long / Float / String / Symbol / Note / Chord / Tuple-of-hashables (8 types). REQUIREMENTS' String-only constraint is OBSOLETE.
- **Constructors:** `(dict K V K V ...)` flat **and** `(dictTuple <<K,V>> ...)` tuple-pair, both ship in 26.1.
- **`each d callback`:** yields `<<key, value>>` tuples; `each` invokes the callback via `~>` internally so a regular 2-arg lambda `(fn Note k, Int v => ...)` works without any lambda-side destructuring. (See Tuple destructuring decision below.)
- **`merge d1 d2`:** ships in 26.1 (only in ROADMAP).

**REQUIREMENTS.md needs updating in the closure phase** — DICT-01/02/03 entries must be rewritten to match ROADMAP scope; current text is stale. Planner may either update REQUIREMENTS.md as part of Phase 26.1 closure (Task N) or note it for a follow-up housekeeping pass.

**Convenience ops carrying over from REQUIREMENTS.md** — composers will hit these idioms constantly per the ergonomics-first memory:

- `(getOr d k default)` — fallback when key missing. Trivial wrapper over `(get) + (has)`.
- `(map d callback)` — transform every value, return new dict. Parallels `(map list ...)`.
- `(filter d predicate)` — keep entries matching predicate. Parallels `(filter list ...)`. Not in either spec but rounds out the functional-collection API.

**Final dict op surface (12 ops):**

| Op | Signature | Source |
|----|-----------|--------|
| `(dict K V K V ...)` | constructor — flat interleaved | ROADMAP |
| `(dictTuple <<K,V>> <<K,V>> ...)` | constructor — tuple-pair | ROADMAP |
| `(get d k)` | lookup, returns V or Nothing | ROADMAP |
| `(getOr d k default)` | lookup with fallback | REQUIREMENTS (carryover) |
| `(set d k v)` | returns new dict with k→v | ROADMAP |
| `(remove d k)` | returns new dict without k | ROADMAP |
| `(has d k)` | Bool | ROADMAP |
| `(keys d)` | `Array[K]` (was `Array[String]` in REQUIREMENTS — generalized) | ROADMAP |
| `(values d)` | `Array[V]` | ROADMAP |
| `(size d)` | Int | ROADMAP |
| `(merge d1 d2)` | last-write-wins (d2 keys override d1) — see Claude's Discretion | ROADMAP |
| `(each d callback)` | side-effect; callback receives unpacked `<<K, V>>` via `~>` | ROADMAP |
| `(map d callback)` | returns new Dict<K, V'> | REQUIREMENTS (carryover) |
| `(filter d predicate)` | returns new Dict<K, V> with matching entries | new |

### Symbol/String charitable equivalence

**Strict separation everywhere.** `#foo` and `"foo"` are NEVER equal, NEVER interchangeable as dict keys.

- `(eq #foo "foo")` returns `false`.
- A `Dict<Symbol, V>` and a `Dict<String, V>` keyed identically have separate buckets.
- `(get d "kick")` on a `Dict<Symbol, Int>` does NOT find `#kick`. It returns `Nothing` (and the type-check at the annotation site should ideally reject the mismatched key type — see Hashable enforcement decision).

**Rationale:** Symbol's whole reason to exist is being a distinct type — interned, pointer-equality, cheaper hash. Charitable equivalence would erase that distinction and reduce Symbol to "an interned String," which is not a useful new type.

This is one explicit deviation from the charitable-interpretation memory's general lean. Justification: that memory governs *composition* errors (a typo'd note name, a missing accidental); type-system distinctions are a different category.

### Hashable enforcement timing

**Disallowed key type → type-check / compile-time error at the annotation site.**

- `Dict<Buffer, Int> bad = ...` — rejected at parse/type-check, with an error pointing at the allowed list.
- The allowed-key list (Int / Long / Float / String / Symbol / Note / Chord / Tuple-of-hashables) lives in `TypeSystem/` (researcher: figure out the cleanest home — likely an `IsHashable()` predicate on `FlowType` or a static allowlist).
- This is NOT charitable interpretation: type-system violations are programmer errors, not composition errors. Catch them early.

**Float key NaN edge case** — special-case NaN-equals-NaN inside Dict.

- `(set d nan v)` succeeds.
- `(get d nan)` returns `v` (Dict-internal equality treats NaN as equal to itself).
- Flow's general `(eq nan nan)` continues to follow IEEE 754 (returns false). Only Dict's hash/eq path special-cases this.
- Rationale: a composer who somehow lands a NaN key (division-by-zero, parsing edge case) shouldn't have a silent dead key.

### `(unpack tuple func)` — runtime first-class apply

**Ships in 26.1 alongside `~>`** as a prefix-form runtime builtin that applies an unpacked tuple to a function value.

```flow
proc renderHit(Note pitch, Beat dur) { ... }
Tuple<<Note, Beat>> entry = <<C4, q>>

entry ~> renderHit                         -- syntactic form (parse-time transform)
(unpack entry renderHit)                   -- equivalent runtime builtin form

Function handler = (get handlers eventType)
event ~> handler                           -- works (parse-time produces handler(...) call site)
(unpack event handler)                     -- explicit; no parse-time gymnastics

(map tuples (fn Tuple<<Int, Int>> t => (unpack t someBinaryOp)))
                                           -- (unpack) is a value-level builtin, composable inside lambdas

(unpack <<>> getFortyTwo)                  -- empty tuple → zero-arg call
(unpack <<5>> doubler)                     -- singleton tuple → one-arg call
```

**Rationale:** Functions are already first-class in Flow (`Function` typed values, closures, HOF passing — see `tests/test_lambdas.flow`). The `~>` operator is a parse-time chain-style ergonomic; `(unpack)` is the value-level S-expression-style equivalent that mirrors Lisp's `(apply f args)`. They're not strictly redundant — `~>` shines in chain syntax; `(unpack)` shines in dynamic-dispatch and HOF-composition patterns.

**Type signature concept:** `unpack: <<T1, ..., Tn>> × ((T1, ..., Tn) => R) → R`. Higher-rank-ish over arbitrary tuple arity — researcher confirms whether Flow's existing `OverloadResolver` handles this or whether `unpack` registers as a special varargs handler (likely the latter, paralleling how `(dict)` accepts interleaved K/V pairs).

**Implementation note:** at runtime, `(unpack)` does the same dispatch as `~>` — unpack tuple components, push as positional args, invoke. ~30 LOC + a 4-theory regression Fact (zero-arg, single-arg, multi-arg, dynamic-Function-value cases).

### Tuple destructuring scope

**Assignment only.** `<<a, b>> = expr` works. `proc` and `fn` parameter lists take whole tuples; composer accesses components via `@N` indexing inside the body.

- ✅ `<<Note pitch, Beat dur>> = (parseNote "C4 q")` — destructures
- ❌ `proc f(<<Note k, Int v>> entry) { ... }` — NOT in 26.1 scope; entry is one Tuple param
- ❌ `(filter list (fn <<a, b>> => (gt a b)))` — NOT in 26.1 scope; lambda takes one Tuple, accesses via `@0`/`@1`

**The iteration case** (the primary tuple use case in this phase) is fully covered by the `~>` unpack operator — `each` invokes its callback as `tuple ~> callback`, so `(each d (fn Note k, Int v => ...))` is a normal 2-arg lambda. No parameter-list destructuring needed.

**Pre-public latitude:** if real usage shows proc/lambda destructuring is missed, add it in a later phase. Memory `project_pre_public_no_legacy_burden` permits this — no deprecation window required. Lower parser surface now is the right tradeoff.

### Claude's Discretion (decisions not asked but inferred from philosophy)

- **`(merge d1 d2)` collision policy:** last-write-wins (d2 keys override d1). Standard convention; ergonomics memory wants the unsurprising default.
- **Insertion-order preservation:** locked by ROADMAP DICT-03; planner uses an order-preserving structure (LinkedHashMap-equivalent — likely `Dictionary<TKey, TValue>` keyed alongside an ordered key array, or a custom `OrderedDictionary<K, V>` wrapper). Researcher to choose.
- **Tuple structural equality:** `<<1, 2>> == <<1, 2>>` returns `true`. Required for Tuple-of-hashables to be usable as a Dict key.
- **Tuple-of-hashables hashable enforcement:** if any component of a Tuple-typed key is non-hashable, the type-checker rejects at the same site as the disallowed-type case. Same error class.
- **Symbol intern table location:** per-execution-context (parallels how `MusicalContext` is scoped in `ExecutionContext`). Researcher confirms; if a global static table is simpler and threading-safe, that's acceptable too — the user-visible behavior (pointer-equality) doesn't change.
- **Empty and singleton tuples:** `<<>>` valid (empty Tuple, type `<<>>` or some unit-marker), `<<x>>` valid (singleton Tuple, type `<<T>>`). ROADMAP-locked.
- **`@N` indexing on Tuple bounds-checking:** compile-time since arity is known from the type annotation. Out-of-bounds `tup@5` on a 2-tuple is a compile error.
- **Symbol uniqueness across module imports:** `#foo` interned globally — same Symbol regardless of which module produced it. Composers expect this; charitable interpretation aligns here (the typed-array hashable allowlist is a different case).
- **Phase 27 implications:** `examples/tutorial.flow` and `examples/showcase.flow` will need new chapters demonstrating Symbol/Tuple/Dict. That's Phase 27's scope, not 26.1's, but planner should leave hooks (a `## Phase 26.1` placeholder section in tutorial.flow if useful).

## Specific Ideas / Anchored Examples

The user asked for these idioms to work end-to-end. Researcher and planner: confirm each one parses and runs after Phase 26.1.

```flow
-- Symbol literal + interning (pointer eq)
Symbol kick = #kick
(eq kick #kick)                  -- true (same intern slot)
(eq kick #snare)                 -- false
(eq #foo "foo")                  -- false (strict separation)

-- Tuple literal + index + destructure
Tuple<<Note, Beat>> entry = <<C4, q>>
Note pitch = entry@0             -- C4
Beat dur   = entry@1             -- q
<<Note p, Beat d>> = entry       -- destructure assignment

-- Tuple equality (structural)
(eq <<1, 2>> <<1, 2>>)           -- true
(eq <<1, 2>> <<1, 3>>)           -- false

-- ~> unpack into multi-arg call (parse-time)
proc renderHit(Note pitch, Beat dur) { ... }
entry ~> renderHit               -- equivalent to (renderHit entry@0 entry@1)

-- (unpack) — runtime first-class apply (S-expr style, mirrors Lisp's apply)
(unpack entry renderHit)         -- same dispatch as the ~> form
Function fnVar = renderHit
(unpack entry fnVar)             -- works with Function-valued variables (dynamic dispatch)
(unpack <<>> getFortyTwo)        -- empty tuple → zero-arg call
(unpack <<5>> doubler)           -- singleton tuple → one-arg call

-- Empty + singleton
Tuple<<>> nothing = <<>>
Tuple<<Note>> just = <<C4>>

-- Dict construction (both forms)
Dict<Symbol, Int> velocities = (dict #kick 90 #snare 70 #hihat 50)
Dict<Symbol, Int> velocitiesT = (dictTuple <<#kick, 90>> <<#snare, 70>> <<#hihat, 50>>)

-- Dict ops
Int v = (get velocities #kick)              -- 90
Int v2 = (getOr velocities #ghost 0)        -- 0 (key absent)
Bool ok = (has velocities #snare)           -- true
Int n = (size velocities)                   -- 3
Array[Symbol] ks = (keys velocities)        -- [#kick, #snare, #hihat] insertion order
Dict<Symbol, Int> louder = (map velocities (fn Symbol k, Int v => (mul v 2)))
Dict<Symbol, Int> hits = (filter velocities (fn _, Int v => (gt v 60)))
(each velocities (fn Symbol k, Int v => (print (concat (str k) " " (str v)))))
                                            -- each unpacks via ~> internally

-- Dict key type rejection (compile error expected)
-- Dict<Buffer, Int> bad = (dict)           -- error: Buffer not hashable

-- Float NaN as key (Dict-special, not IEEE general)
Dict<Float, Int> nanD = (dict nan 42)       -- succeeds
Int found = (get nanD nan)                  -- 42 (Dict-internal NaN-eq-NaN)

-- Tuple-of-hashables as key
Dict<Tuple<<Note, Beat>>, Int> beatMap = (dict <<C4, q>> 1 <<D4, h>> 2)
(get beatMap <<C4, q>>)                     -- 1
```

These nine blocks are the acceptance shape. Anything that doesn't parse or run as shown is a defect in 26.1, not a deferred follow-up.
