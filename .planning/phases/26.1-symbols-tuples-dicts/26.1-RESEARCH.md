## Summary

Phase 26.1 layers three tightly-coupled language additions on top of the prefix-only base shipped in Phase 26: a Symbol primitive (`#foo`, interned), a Tuple type with literal/index/destructure syntax (`<<a, b>>`, `tup@N`, `<<a, b>> = expr`), and a generic `Dict<K, V>` with hashable-key enforcement. The work is heavy on the lexer / parser / type-parser, light on the runtime (the existing `Value` + `OverloadResolver` machinery handles most of the work), and adds 14 dict ops + `(unpack)` to the stdlib. No new NuGet packages required — `System.Collections.Generic.OrderedDictionary<TKey, TValue>` (.NET 9+, available in .NET 10) gives insertion-order preservation + custom `IEqualityComparer<TKey>` for the NaN-as-key special case for free.

The tightest design question is `<<` / `>>` token disambiguation. Today the lexer emits separate `LessThan` / `GreaterThan` tokens (no `<<` two-char token), and `<` / `>` are used only by `Lazy<T>` type parsing and by note-stream-internal articulations (`>` is accent). Two-token-matching at the parser level (look for two consecutive `LessThan` to recognize `<<`) plus introducing fresh `LessLess` / `GreaterGreater` two-char lexer tokens at expression-start (and inside type-annotation context) cleanly separates Tuple delimiters from comparison-context `<` `>` without disrupting the existing `Lazy<T>` parser. The `Dict<K, V>` annotation reuses single `<` / `>` (paralleling `Lazy<T>`) — the only `>>>` ambiguity to handle is `Dict<Symbol, Tuple<<Note, Beat>>>` where three consecutive `GreaterThan` tokens close a tuple-of-two and a dict-of-one — which the parser handles trivially because each closer is consumed at a different parse depth.

`~>` is implemented as a parse-time transform that mirrors the existing `->` flow operator: at parse time, if the right-hand side is a function-call-like form, the LHS tuple's components are unpacked into positional arguments. On non-tuple LHS (or unknown-arity LHS at parse time), the parser falls through to the existing `->` semantics, satisfying the charitable-interpretation memory. The runtime `(unpack)` builtin is a varargs registration that mirrors how `(list)` is registered today (varargs `Void`) plus a special second-arg `Function`-typed signature.

**Primary recommendation:** Implement in 5 dependency waves (Symbol → Tuple → `~>` + `(unpack)` → Dict types/keys → Dict ops + closure), single mega-commits per wave matching Phase 26's D-13 precedent. Skip Migrate26-style migration script — no in-repo `.flow` files use any of the new syntax.

## Open Technical Questions Resolved

### Q1 — Lexer collisions for `<<` / `>>`

**Question:** Does the existing lexer have any token that begins with `<` or `>` that could ambiguate?

**Findings [VERIFIED: SimpleLexer.cs:139–140; Parser.NoteStream.cs:399, 434; TypeParser.cs:38–48]:**
- `<` and `>` lex one-at-a-time as `LessThan` / `GreaterThan` (no `<<`/`>>` two-char tokens today).
- `<` is consumed by `TypeParser.ParseType` for `Lazy<T>` only (line 38).
- `>` is consumed by (a) `TypeParser.ParseType` closing `Lazy<T>` (line 46) and (b) `Parser.NoteStream.cs:399` as note-stream articulation accent (`C4q>`).
- No infix comparison (`a < b`) exists — comparisons are prefix builtins `(lt)`, `(gt)`, `(lte)`, `(gte)` per `std.flow:94–97`.
- `<=` and `>=` are NOT tokens today (no `LessEqual`/`GreaterEqual` enum values per `TokenType.cs`).
- No `<<<` form exists. No shift-left/right operators.

**Recommendation:** Introduce dedicated `LessLess` and `GreaterGreater` two-char tokens, emitted ONLY at expression-start positions (the same gate `TryLexSignedNumber` uses at `SimpleLexer.cs:345–358`). At all other positions, emit one `LessThan`/`GreaterThan` per character — this preserves note-stream `>` accent parsing AND `Lazy<T>` parsing untouched. The expression-start gate prevents `>>` inside note streams from being misread.

**Confidence:** HIGH.

### Q2 — `<<` / `>>` as paired delimiters AND type-annotation generics simultaneously

**Question:** In `Tuple<<Note, Beat>>` the outer `<<` `>>` come right after a type name. In `Dict<K, V>` it's single `<` `>`. Both forms in `Dict<Symbol, Tuple<<Note, Beat>>>` — does `>>>` need special handling like Java's `>>` ambiguity?

**Findings:** Java's `>>` ambiguity arose because `>>` was already a shift operator AND a generic close-pair (`List<List<T>>`). Flow has neither — `>>` doesn't exist as an operator. The lexer's expression-start gate (Q1 recommendation) already filters when `LessLess`/`GreaterGreater` can be emitted: only at positions where a tuple LITERAL could start. **Type-annotation context is a parser-internal walk, not a lex-time concern.**

**Recommendation:** TypeParser handles `Tuple<<...>>` by reading the next two tokens after `Tuple` directly. It expects two consecutive `LessThan` tokens (NOT `LessLess`). Then parses the type list. Then expects two consecutive `GreaterThan` tokens. So `Dict<Symbol, Tuple<<Note, Beat>>>` lexes as `Dict | < | Symbol | , | Tuple | < | < | Note | , | Beat | > | > | >` — 13 tokens, all `LessThan`/`GreaterThan` because the lexer is at type-annotation context (not expression-start). The parser walks them at the right depth: Dict opens its `<`, parses Symbol, comma, parses Tuple's `<` `<`, Note, comma, Beat, Tuple's `>` `>`, then Dict's `>`. No ambiguity — each generic-close is consumed at a unique parse depth. Java's "split `>>` into two `>`" hack is not needed.

**Implication for `LessLess`/`GreaterGreater` two-char tokens:** they ONLY apply to TUPLE LITERALS at expression-start. Type-annotation context uses one-char `LessThan`/`GreaterThan` exclusively. This is internally consistent because type annotations occur in known parser positions (after a type keyword, after `=`, etc.) and never at expression-start.

**Confidence:** HIGH.

### Q3 — Symbol intern table location

**Confidence:** HIGH.

### Q5 — `~>` operator: parse-time vs runtime dispatch

**Findings [VERIFIED: Parser.cs:689–734]:** The existing `->` is a parse-time TRANSFORM but only for the ergonomic shape `x -> func` → `func(x)` and `x -> func(arg)` → `func(x, arg)`. When the right-hand side isn't a recognizable call shape (e.g., `5 -> someValue` where `someValue` is a Function-typed variable), the parser FALLS BACK to wrapping in a `FlowExpression` AST node and the EVALUATOR (line 279) does the runtime dispatch.

**Recommendation:** Mirror this exact pattern for `~>`. Parser-side: in `ParseFlowExpression` (line 689), also `Match(TokenType.TildeArrow)`. When the RHS is a `VariableExpression` or `FunctionCallExpression`, emit a tuple-aware transform; otherwise emit a `TupleUnpackFlowExpression` AST node. Evaluator-side: `EvaluateTupleUnpackFlow` checks `leftVal.Type is TupleType` → unpacks components into positional args; else falls through to the existing `EvaluateFlowExpression` (single-arg `->`) semantics, satisfying the charitable-interpretation success criterion.

**Critical detail:** Even when the parser-side transform fires (RHS is a call shape), it can't statically know the tuple's arity (variables aren't typed at parse time in Flow). So the parser must DEFER unpacking — emit a `TupleUnpackFlowExpression` regardless of RHS shape, OR the parser must emit a placeholder FunctionCallExpression with a runtime-resolved arg list. **Simpler choice: always emit `TupleUnpackFlowExpression` and do unpacking in the evaluator.** This matches how Flow's `->` already handles the runtime-Function-value case (line 284).

**Confidence:** HIGH.

### Q6 — `(unpack)` runtime builtin signature

**Findings [VERIFIED: BuiltInFunctions.cs:464–468 (list); BuiltInFunctions.cs:856–865 (each/map/filter); BuiltInFunctions.cs:870–893 (oscillator with Function arg)]:**
- Varargs registration pattern: `new FunctionSignature("list", [VoidType.Instance], IsVarArgs: true)` then `Register("list", sig, Collections.List)`.

Acceptance test cases:

- `(unpack <<5>> doubler)` — singleton → 1 arg
- `(unpack <<C4, q>> renderHit)` — multi-arg

**Confidence:** HIGH.

### Q8 — Order-preserving Dict storage

**Findings [VERIFIED via Microsoft Learn doc fetch, .NET 10 API]:**
- `System.Collections.Generic.OrderedDictionary<TKey, TValue>` was introduced in .NET 9 [CITED: https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.ordereddictionary-2?view=net-10.0].
- Available in .NET 10. Preserves insertion order. Access by key OR by integer index. Implements `IDictionary<TKey, TValue>`, `IList<KeyValuePair<TKey, TValue>>`, `IReadOnlyDictionary<TKey, TValue>`, `IReadOnlyList<KeyValuePair<TKey, TValue>>`.
- Constructors accept `IEqualityComparer<TKey>` — directly enables the NaN-as-key special case (Q9).
- Performance: list-like complexity for index ops, dict-like complexity for key lookups.

**Recommendation:** Use `OrderedDictionary<Value, Value>`. Wrap in a new `DictData` class that:
- Holds the underlying `OrderedDictionary<Value, Value>` + the `DictType` (so type info is preserved even when the dict is empty).
- Exposes immutable update methods: `WithSet(k, v)`, `WithRemove(k)`, `Merge(other)` — each returns a NEW `DictData` (copy + apply). Fits Flow's immutability story.
- Constructor takes the `DictType` and uses a custom `IEqualityComparer<Value>` derived from key type (NaN-special-cased when key type is FloatType).

**Alternatives considered:**
- `Dictionary<TKey, TValue> + List<TKey>` — would work but doubles state, harder to keep in sync, more code.
- `KeyedCollection<TKey, KeyValuePair>` — heavier, more abstraction than needed.
- Roll our own — wasted effort given BCL has the right tool.

**Confidence:** HIGH.

### Q9 — NaN-as-key special case

**Findings:** Standard .NET `double` equality returns false for NaN-vs-NaN (IEEE 754). `Dictionary<double, V>` uses `EqualityComparer<double>.Default` which inherits IEEE semantics — so a NaN insert AND lookup miss silently. CONTEXT requires NaN-as-self in Dict only, NOT in general `(equals nan nan)`.

**Recommendation:** Pass a custom `IEqualityComparer<Value>` to `OrderedDictionary<Value, Value>`'s constructor. The comparer is constructed at `DictData` construction time (when the `DictType` is known), parameterized by key type:

```csharp
public sealed class DictKeyComparer : IEqualityComparer<Value> {
    private readonly FlowType _keyType;
    public DictKeyComparer(FlowType keyType) => _keyType = keyType;
    public bool Equals(Value? a, Value? b) {
        if (a is null || b is null) return ReferenceEquals(a, b);
        // Float NaN special case — Dict-internal only.
        if (_keyType is FloatType && a.Data is double ad && b.Data is double bd) {
            if (double.IsNaN(ad) && double.IsNaN(bd)) return true;
            return ad == bd;
        }
        // Symbol pointer-equality fast path.
        if (_keyType is SymbolType) return ReferenceEquals(a.Data, b.Data);
        // Tuple structural equality.
        if (_keyType is TupleType) return TupleStructuralEquals(a, b);
        // Default: existing StrictEquals (Utils.cs:90).
        return Utils.StrictEquals(a, b);
    }
    public int GetHashCode(Value v) {
        if (v.Data is double d && double.IsNaN(d)) return 0; // NaN canonical hash
        return v.Data?.GetHashCode() ?? 0;
    }
}
```

This pattern keeps Flow's general `(equals nan nan)` (which goes through `Utils.LooseEquals` at `BuiltInFunctions.cs:367`) untouched.

**Confidence:** HIGH.

## Common Pitfalls

### Pitfall 1: `>>` consumed by note-stream articulation parser

**What goes wrong:** Note streams use `>` as the accent articulation (`Parser.NoteStream.cs:399`). If `LessLess`/`GreaterGreater` two-char tokens are emitted unconditionally, `| C4q>>... |` would lex `>>` as `GreaterGreater` and break the existing accent test.

**Why it happens:** Tuple delimiters share the `>` character with articulation accent.

**How to avoid:** Gate two-char `<<`/`>>` emission on `_lastEmittedType` being in the expression-start set (LParen / Comma / LBracket / Arrow / Assign / Pipe / Semicolon / Identifier / null). This is the exact gate `TryLexSignedNumber` uses (`SimpleLexer.cs:345–358`). Inside note streams the previous token is typically `NoteLiteral` or `Underscore`, which are NOT in the gate — so `>` lexes as a single `GreaterThan` token and the articulation parser still works.

**Warning signs:** Any existing test that uses `>` accent (e.g., `tests/test_articulations.flow` if it exists, or `tests/test_dynamics.flow`) failing after Wave 2.

### Pitfall 2: `~>` with `Function`-typed RHS (dynamic dispatch)

**What goes wrong:** Parser-side `~>` transform tries to read RHS as `VariableExpression` or `FunctionCallExpression` (paralleling `->` at `Parser.cs:702–722`). When RHS is a `Function`-typed variable, the variable IS a `VariableExpression` — so the transform tries to emit `func(tup@0, tup@1, …)`, but at parse time we don't know tuple arity (variable types aren't resolved at parse time).

**Why it happens:** Parse-time arity is unknown for tuple-typed variables.

**How to avoid:** Don't transform at parse time. Always emit `TupleUnpackFlowExpression` AST node. Evaluator does the unpacking at runtime, where the tuple's `IReadOnlyList<Value>` is in hand. CONTEXT example block 5 (dynamic Function-value) is the canary — if it works, this pitfall is closed.

**Warning signs:** Test 5 of `test_unpack_runtime.flow` fails with `Cannot apply pipe operator ~> to non-function type`.

### Pitfall 3: NaN-key bleeds into general equality

**What goes wrong:** Implementing NaN-as-self in `Utils.StrictEquals` (the wrong place) would change `(equals nan nan)` from `false` to `true` globally — violates CONTEXT's explicit scope (Dict-only).

**Why it happens:** Tempting to put the special-case in the central equality path because Dict reuses it.

**How to avoid:** Pass a dedicated `IEqualityComparer<Value>` to the `OrderedDictionary` constructor. The comparer is parameterized by `DictType.KeyType` — when key type is `FloatType`, the comparer's `Equals` does NaN-special-casing. `Utils.StrictEquals` is NEVER touched.

**Warning signs:** A regression in `test_humanize.flow` or any test that exercises `(equals nan nan)` returning anything other than false.

### Pitfall 4: Symbol intern table leaks across REPL sessions / tests

**What goes wrong:** A static global intern table accumulates state across `FlowEngine` spin-ups; xUnit parallel test runs can race on it; one test's `#foo` lingers and pointer-eq-matches a later test's `#foo` (which is fine semantically but couples tests).

**Why it happens:** "Intern table" is conventionally global in many languages.

**How to avoid:** Place on `ExecutionContext` per Q3 recommendation. Each `FlowEngine` constructs a fresh `ExecutionContext` (verified via `flow-interpreter` patterns), so xUnit-level isolation is preserved.

**Warning signs:** Tests mysteriously pass in isolation but fail under `dotnet test` parallel runs.

### Pitfall 5: `Dict<K, V>` parsing colliding with `Lazy<T>` parser

**What goes wrong:** TypeParser's `Lazy<T>` branch (line 33) is the only existing `Identifier + LessThan` generic pattern. Adding `Dict` and `Tuple` as siblings could subtly break the dispatch order — e.g., `Lazy<Dict<Int, Int>>` exercises both nestings.

**Why it happens:** Generic type parsers are recursive and order-sensitive.

**How to avoid:** Add `Dict` and `Tuple` branches in TypeParser BEFORE the plural-form check (line 61) but AFTER the `Lazy` branch. Each branch dispatches by `token.Text == "Dict"` etc. The recursion path goes through `ParseType` for the inner types — same shape as `Lazy<T>`.

**Warning signs:** `Lazy<Dict<Int, Int>>` annotation fails to parse, or the inner `Dict` is treated as the outer Lazy.

### Pitfall 6: `(each)` callback dispatch differs between Dict and Array

**What goes wrong:** Existing `(each Array Function)` at `BuiltInFunctions.cs:856` invokes the callback with ONE arg (the element). For Dict, CONTEXT requires the callback to receive TWO args (key, value) via `~>` unpack of a `<<K, V>>` tuple.

**Why it happens:** Same builtin name, different dispatch shape.

**How to avoid:** Register a SEPARATE `(each DictType FunctionType)` overload that dispatches via `DictFunctions.Each` — which constructs `<<k, v>>` tuples per entry and invokes via the same dispatch as `~>` (i.e., unpacks the tuple into 2 positional args). Don't try to overload `Collections.Each` itself — keep dict logic in `DictFunctions.cs`. The OverloadResolver picks the right one by arg-0 type.

**Warning signs:** `test_dict_ops.flow` `(each)` test crashes with "No matching overload for 'each' with arg types (Dict, Function)" — means the dict-side registration is missing.

### Pitfall 7: `<<>>` empty tuple type ambiguity in annotation

**What goes wrong:** `Tuple<<>>` is a valid empty-tuple type annotation. The TypeParser sees `Tuple` `<` `<` `>` `>`. Naive parsing: "two `<` consumed; now look for type list; immediately see `>`; OK empty list; consume two `>`s." But the empty-list path could be confused with malformed annotation.

**Why it happens:** Empty arities are valid; parsers often forget edge-case minimums.

**How to avoid:** Explicit early-return path in the Tuple-type parser: after consuming `< <`, if next token is `>` (closing), check it's followed by a second `>`; if yes, return `TupleType(empty list)`. Mirror this exact early-return for `<<>>` literal in the expression parser.

**Warning signs:** `Tuple<<>> nothing = <<>>` fails to parse with a misleading "Expected type name" error.

// Source: NEW — flow-lang/Runtime/DictKeyComparer.cs
public sealed class DictKeyComparer : IEqualityComparer<Value>
{
    private readonly FlowType _keyType;
    public DictKeyComparer(FlowType keyType) => _keyType = keyType;

    public bool Equals(Value? a, Value? b)
    {
        if (a is null || b is null) return ReferenceEquals(a, b);
        // Float NaN special case — Dict-internal only.
        if (_keyType is FloatType && a.Data is double ad && b.Data is double bd)
        {
            if (double.IsNaN(ad) && double.IsNaN(bd)) return true;
            return ad == bd;
        }
        // Symbol pointer-equality fast path.
        if (_keyType is SymbolType) return ReferenceEquals(a.Data, b.Data);
        // Default: delegate to existing structural equality.
        return Utils.StrictEquals(a, b);
    }

    public int GetHashCode(Value v)
    {
        if (v.Data is double d && double.IsNaN(d)) return 0;
        return v.Data?.GetHashCode() ?? 0;
    }
}

## Risks & Landmines

### Lexer ambiguity (`<<` / `>>` vs note-stream `>` accent)

**Risk:** Wave 2's two-char `LessLess`/`GreaterGreater` tokens fire inside note streams and break existing accent parsing.

**Mitigation:** Expression-start `_lastEmittedType` gate (Pitfall 1). Run full `tests/test_*.flow` suite after Wave 2 — any test using `>` accent will surface a regression immediately.

### Generic-parsing edge case (`Dict<Symbol, Tuple<<Note, Beat>>>`)

**Risk:** Three consecutive `>` close two distinct generic levels; nested generic parsing must consume the right token at the right depth.

**Mitigation:** Q2 analysis shows this is naturally handled by recursive descent — each parser scope consumes ONE `>` before returning. The `Tuple<<...>>` parser consumes TWO `>` (its closer); the surrounding `Dict<...>` consumes ONE. No `>>` two-char token is ever in play in type-annotation context. Validation: an explicit nested-generic test in `DictKeyTypeFacts.cs`.

### NaN-key bleeds into general equality (Pitfall 3)

**Risk:** Implementing in `Utils.StrictEquals` instead of `DictKeyComparer` breaks `(equals nan nan) → false` globally.

**Mitigation:** Code review of Wave 4 PR diff — verify `Utils.cs` is NOT touched. Add the regression Fact `DictNanKeyFacts.GeneralEqualityUnchanged` that explicitly tests `(equals nan nan) → false`.

### Symbol intern table threading

**Risk:** `ExecutionContext.SymbolInternTable` accessed from multiple threads (parallel test runs, future audio-render threads).

**Mitigation:** Wrap access in `lock(SymbolInternTable)` — mirrors `ExecutionContext.RandLock` pattern (line 36). Cheap; not a hot path.

### `<<>>` empty tuple type ambiguity (Pitfall 7)

**Risk:** `Tuple<<>>` annotation fails to parse because the type-list parser expects at least one type.

**Mitigation:** Explicit empty-arity early-return in TupleType parser. Add test `TupleFacts.EmptyAnnotationParses`.

### `(each)` overload disambiguation between Array and Dict

**Risk:** OverloadResolver picks the wrong `(each)` overload when arg 0 is a Dict.

**Mitigation:** Pitfall 6 — register a separate dict-typed `(each)` overload. Validate via `DictOpsFacts.EachUnpacks` Fact AND smoke script.

### Phase 18 / 25 byte-identical determinism regression

**Risk:** Subtle change to overload resolution priority surfaces a different overload pick for an existing tutorial/showcase line, changing rendered bytes.

**Mitigation:** Phase 18 `ByteIdenticalShowcaseTests` and Phase 25 `ByteIdenticalShowcaseGaussianTests` are existing xUnit guards. The planner's wave-merge gate runs them. Phase 26.1 should NOT add new Symbol/Tuple/Dict references to `tutorial.flow` or `showcase.flow` (that's Phase 27's job per CONTEXT § Claude's Discretion + Phase 27 ROADMAP entry).

### TupleType.AnyArity sentinel handling in OverloadResolver

**Risk:** `(unpack)`'s registration uses a sentinel "any-tuple" type; OverloadResolver's specificity scoring may not handle it correctly relative to a more specific tuple type if both register.

**Mitigation:** Mirror the `ArrayType(VoidType.Instance)` precedent (`BuiltInFunctions.cs:470`) — that exact pattern is used by `(list)`, `(map)`, `(filter)` and the resolver already handles it. Only ONE `(unpack)` overload exists; no specificity tie-break is needed.

## Open Questions (RESOLVED)

1. **Should `(each)` callback receive `<<K, V>>` already-unpacked or as a single tuple arg?**
   - What we know: CONTEXT requires user-facing `(fn Symbol k, Int v => ...)` 2-arg lambdas. Implementation must invoke the callback as if it were `tuple ~> callback`.
   - What's unclear: Does the Dict's `(each)` registration take a `Function`-typed callback that internally always gets 2 positional args (i.e., the dict-side does the unpacking), OR does it pass the tuple and rely on the user to write `(fn Tuple<<Symbol, Int>> t => ...)`? CONTEXT § Tuple destructuring scope explicitly says lambda parameter destructuring is OUT OF SCOPE — so the answer is: `each` does the unpacking internally before calling the lambda. The lambda is a normal 2-arg lambda.
   - Recommendation: implementation always unpacks into 2 positional args before invoking the callback. Document this in the `(each Dict)` registration site with a comment cross-referencing the CONTEXT decision.
   - **RESOLVED:** Implemented in Plan 26.1-05 Task 2 — `DictFunctions.Each` (and `Map`/`Filter`) constructs a 2-element positional arg list `[kv.Key, kv.Value]` before invoking the callback, per recommendation above. The `(each Dict)` registration site at `BuiltInFunctions.cs RegisterDict` is documented with a Pitfall-6 cross-reference comment.

2. **Should `(map d cb)` allow the callback to RETURN a tuple to change the key?**
   - What we know: CONTEXT says "(map d callback) returns new Dict<K, V'>" — V changes, K does not.
   - What's unclear: Whether the implementation allows callback signature `(fn K, V => Tuple<<K', V'>>)` to also remap keys (would let `map` do double duty as `mapKeys`).
   - Recommendation: keep V-only. Match the CONTEXT contract exactly. If `mapKeys` is wanted, defer to a future phase. (Aligns with `project_pre_public_no_legacy_burden` — easy to add later.)
   - **RESOLVED:** Implemented in Plan 26.1-05 Task 2 — `DictFunctions.Map` returns `Dict<K, V'>` where K is preserved unchanged and only V is transformed. `mapKeys` deferred to a future phase per recommendation above.

3. **Are tuples printable consistently with Flow's existing `(str)` overloads?**
   - What we know: `std.flow:14-32` registers `(str)` for many primitive/special types but not for arrays (arrays use `Value.ToString()` directly via `Value.cs:234`).
   - What's unclear: Should we add `(str Tuple<...>)` and `(str Dict<...>)` overloads, or rely on `Value.ToString()` for diagnostic prints?
   - Recommendation: rely on `Value.ToString()` (extend at `Value.cs:229-240`). Adding `(str)` overloads for generic types complicates the registration; the test pattern `(print (str result))` works because `(str)` for `Voids` (line 28) already accepts arrays via the convertibility path. Tuples can convert to `Void[]` for printing if needed — but cleaner to handle at `Value.ToString()`.
   - **RESOLVED:** Implemented in Plan 26.1-03 Task 2 (Tuple ToString branch) and Plan 26.1-05 Task 1 (Dict ToString branch) — both extend `Value.ToString()` at the existing switch site rather than adding new `(str)` overloads, per recommendation above. Dedicated `(str Tuple<...>)` / `(str Dict<...>)` overloads are out of scope for Phase 26.1; if cleaner formatting is wanted later it can be added in Phase 27 closure.
