## Decisions Made

- **Adapted plan's `<<C4, q>>` examples to authorable type pairs.** The CONTEXT block proposes `Tuple<<Note, Beat>> = <<C4, q>>` as the canonical idiom — but `q` has no Beat-construction path in user source. The `q` lexer suffix exists only as a duration suffix on note literals (`C4q`), and `Beat` has no value-construction builtin in 26.1. Three impacts:
  - `AnnotationParse_TupleOfNoteAndBeat` fact: switched to default-init (no `=`) — still verifies the annotation parses, which is the fact's name's stated purpose.
  - `Destructure_TypedSlots_NoteBeat` fact: switched to `Tuple<<Note, Note>> = <<C4, D4>>` — same destructure code path; the type-check branch in `ExecuteTupleDestructure` doesn't differ between Note+Note and Note+Beat.
  - `tests/test_tuple_literal.flow` + `test_tuple_destructure.flow`: same Note+Note substitution.
  Future ergonomic addition (out of 26.1 scope): a `Beat q` constant in `std.flow` or a `(beat 0.25)` builtin would let CONTEXT's exact idiom work. Documented as a follow-up but not blocking 26.1 acceptance.

- **Extended lexer expression-start gate with `LessLess`.** Plan's revision-1 set listed RParen/RBracket/RBrace + 7 literal-end tokens + GreaterGreater, but did NOT include LessLess. Without LessLess in the gate, the empty-tuple literal `<<>>` breaks: after lexing `<<` → LessLess, the next `>>` finds prev=LessLess (not in gate), falls through to two single-char `>` tokens, and the parser's `Expect(GreaterGreater)` fails. Adding LessLess makes `>>` immediately following `<<` lex as a single GreaterGreater. Confirmed safe by re-running `tests/test_dynamics.flow` (still GREEN — note-stream context never sees prev=LessLess).

- **Auto-added "Tuple" to Parser.IsTypeKeyword.** Plan added Tuple to TypeParser (the type-annotation parser invoked from ParseVariableDeclaration) but missed Parser.IsTypeKeyword which is the GATE that triggers `ParseVariableDeclaration` when seeing `Tuple<<Note, Beat>> entry = ...`. Without it, the parser sees `Tuple` as a regular identifier, tries to parse the line as an expression, and hits `<<` unexpectedly. Same fix-pattern as Wave 1's Symbol addition.

- **Auto-added TupleType recursion in Interpreter.CreateDefaultValue.** Without it, default-init Tuple variables fall through to the `_ => Value.Void()` arm, then the IsCompatibleWith check in ExecuteVariableDeclaration fails (Void → TupleType is not compatible). Recursive per-position default-construction mirrors how ArrayType creates an empty-array default.

- **`TupleType.GetHashCode` AnyArity special case.** Two `AnyArity` sentinels with empty ElementTypes hash the same regardless of the (empty) element list — needed because `Equals(AnyArity, AnyArity)` returns true under any-arity semantics, and `Equals=>HashCode` contract requires hash equality. Implemented via a sentinel string in the HashCode builder when `IsAnyArity` is true.
