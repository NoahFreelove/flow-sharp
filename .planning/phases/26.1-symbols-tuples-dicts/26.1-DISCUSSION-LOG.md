## Area 2 — Symbol/String charitable equivalence

**Question:** "How should `#foo` (Symbol) and `\"foo\"` (String) interact?"

**Options presented (single-select):**
1. Strict separation everywhere (Recommended)
2. Charitable in Dict lookup only
3. Fully charitable everywhere

**User selection:** 1 (Strict separation everywhere).

**Locked decision:** `(eq #foo "foo")` returns false. Distinct dict buckets. Symbol's value as a type is preserved.

**Notable framing:** This is an explicit, justified deviation from `feedback_charitable_interpretation`. That memory governs *composition* errors (typo'd note, missing accidental), not type-system distinctions. Symbol's reason to exist IS the type distinction; charitable equivalence would erase it.

## Area 4 — Tuple destructuring scope

**Question:** "Where does tuple destructuring work in Phase 26.1?"

**Options:**
1. Assignment only (matches ROADMAP exactly) (Recommended)
2. Assignment + proc params
3. Assignment + proc + lambda params

**User selection:** 1 (Assignment only).

**Locked decision:** `<<a, b>> = expr` works. proc/lambda params take whole tuples; composer uses `@N` indexing inside body. The `~>` unpack operator handles the iteration case (`(each d (fn K k, V v => ...))` — `each` invokes the callback as `tuple ~> callback` internally), so lambda destructuring isn't needed for the primary tuple use case.

**Memory hook:** `project_pre_public_no_legacy_burden` permits adding proc/lambda destructuring later if real composer usage shows it's missed. Lower parser surface now is the right tradeoff.

## Area 5 — `(unpack TUPLE FUNC)` first-class apply (added post-initial-discussion)

User asked: "Are functions first-class citizens in flow lang? I think we should add that in as well, something cool like `(unpack TUPLE FUNC)` and it will apply the tuple unpacked to func."

**Pre-question check:** Verified Flow already supports first-class functions. `tests/test_lambdas.flow` shows: `Function`-typed variables, type annotations `(Int => Int)` / `(Int, Int => Int)`, closures capturing lexical scope, passing `Function`-typed variables to higher-order functions like `(map list scaler)`. Lambda + Function type are mature in v1.2; Phase 26.1 inherits this without change.

**Question:** "How should `(unpack TUPLE FUNC)` slot into the work?"

**Options presented:**
1. Add to Phase 26.1 scope (Recommended)
2. Capture as deferred, decide in Phase 26.2 or 27
3. Don't add — `~>` is enough

**User selection:** 1 (Add to Phase 26.1 scope).

**Locked decision:** `(unpack tuple func)` ships in 26.1 alongside `~>`. New requirement TUP-11 added to REQUIREMENTS.md; ROADMAP success criteria expanded from 7 to 9 (TUP-11 + Float NaN edge case made explicit). Acceptance shape: empty/single/multi-arg cases plus the dynamic `Function`-valued-variable case.

**Rationale captured:** `~>` and `(unpack)` are not strictly redundant — `~>` is a parse-time chain-style ergonomic, `(unpack)` is a value-level S-expr-style equivalent that mirrors Lisp's `(apply f args)`. Memory `feedback_language_philosophy` (S-expr style) and `feedback_ergonomics_priority` both push for shipping both forms.
