## Decisions Made

- **Namespace `FlowLang.StandardLibrary.Dict` instead of `FlowLang.StandardLibrary.Collections`:** the latter collides with the existing static class `FlowLang.StandardLibrary.Collections` (Collections.cs). Directory layout still uses `StandardLibrary/Collections/` per CONTEXT § Architectural Responsibility Map; only the C# namespace differs.
- **Always-emit `TupleUnpackFlowExpression` from the parser (no parse-time arity peek):** simplest implementation per RESEARCH Q5; mirrors how `->` falls through to `FlowExpression` when RHS isn't a recognizable call shape. Tuple arity isn't statically known at parse time anyway.
- **Charitable non-tuple LHS fallthrough:** `5 ~> doubleIt` → `(doubleIt 5)` (single-arg). Per ROADMAP success criterion 3, ergonomics-priority memory. Avoids the rigid alternative of erroring "non-tuple LHS to ~>".

**3. [Rule 1 - Bug] Plan-specified `proc` syntax doesn't match Flow's actual grammar**
- **Found during:** Task 2 (running un-skipped Facts → `Expected ':' after parameter type`)
- **Issue:** Plan's example bodies used `proc f (Int x) { ... }` (brace-style, un-colon'd params) — both Facts (5 of 6) and smoke scripts. Flow's actual grammar (Parser.cs:265, test_comments.flow:23) requires `proc f (Int: x)` with `end proc` close — see `internal proc add (Int: a, Int: b)` in std.flow:42.
- **Fix:** Updated all `proc` declarations in Facts and smoke scripts to use Flow's grammar. Added explanatory note in DynamicFunctionValue's source comment.
- **Files modified:** flow-lang.Tests/Unit/Phase26_1/UnpackFlowFacts.cs, flow-lang.Tests/Unit/Phase26_1/UnpackRuntimeFacts.cs, tests/test_unpack_flow.flow, tests/test_unpack_runtime.flow
- **Verification:** All 6 Facts GREEN; smoke scripts emit PASSED sentinels.
- **Committed in:** d628870 (Wave 3 mega-commit)

**4. [Rule 1 - Bug] Flow operator `~>` not allowed inside parens**
- **Found during:** Task 2 (running un-skipped Facts → `Unexpected token TildeArrow '~>' at <test>:7:12`)
- **Issue:** Plan had `Int r = (t ~> add3)` — but Flow's flow operators (`->`/`~>`) live at top-level / RHS-of-assignment positions, not inside `(...)`. Inside parens the parser sees `(...)` as a function-call shape and fails on `~>` between args. Reference: `tests/test_lambdas.flow:97` (`Int r17 = 5 -> doubler`).
- **Fix:** Removed parens around the flow expressions — `Int r = t ~> add3` (Facts and smoke scripts).
- **Files modified:** flow-lang.Tests/Unit/Phase26_1/UnpackFlowFacts.cs, tests/test_unpack_flow.flow
- **Verification:** UnpackFlowFacts 2/2 GREEN.
- **Committed in:** d628870 (Wave 3 mega-commit)

**5. [Rule 1 - Bug] Zero-arg proc auto-call defeats Function-value pass**
- **Found during:** Task 2 (running ZeroArg fact → `No matching overload for function 'unpack' with argument types (Tuple<<>>, Int)`)
- **Issue:** Plan had `proc getFortyTwo () { 42 }` then `(unpack e getFortyTwo)`. But `EvaluateVariable` (ExpressionEvaluator.cs:150) auto-calls 0-arg functions when referenced as a bare identifier — so `getFortyTwo` evaluates to `42` (Int) BEFORE `(unpack)` sees it. The OverloadResolver then can't find `unpack(Tuple<<>>, Int)`. (Single-/multi-arg procs avoid this because the 0-arg resolution fails and the code path falls through to returning `Value.Function(overloads[0])`.)
- **Fix:** Switched to a Function-typed lambda binding: `Function getFortyTwo = fn => 42`. Same acceptance shape; passes the function as a value to `(unpack)`.
- **Files modified:** flow-lang.Tests/Unit/Phase26_1/UnpackRuntimeFacts.cs, tests/test_unpack_runtime.flow
- **Verification:** UnpackRuntimeFacts.ZeroArg_EmptyTuple GREEN.
- **Committed in:** d628870 (Wave 3 mega-commit)
