    **FIX-02: Section bare expression capture**

    Per research (Pitfall 2): Collect ALL expression statement results during section body execution, not just _lastExpressionValue.

    In Interpreter.cs, modify `ExecuteSectionDeclaration` (around line 336-377):

    Replace the body execution and collection logic with:
    ```csharp
    private void ExecuteSectionDeclaration(SectionDeclaration section)
    {
        // Check for duplicate section names (unchanged)
        if (_context.SectionRegistry.ContainsKey(section.Name))
        {
            _errorReporter.ReportError(
                $"Section '{section.Name}' is already defined", section.Location);
            return;
        }

        _context.PushFrame();
        try
        {
            var musicalContext = _context.GetMusicalContext();

            // Track bare expression results during body execution
            var bareExpressionSequences = new List<SequenceData>();

            foreach (var stmt in section.Body)
            {
                ExecuteStatement(stmt);

                // Capture bare expressions that produce sequences
                if (stmt is ExpressionStatement && _lastExpressionValue?.Data is SequenceData exprSeq)
                {
                    bareExpressionSequences.Add(exprSeq);
                }

                if (_returnValue != null) break;
            }

            // Collect named Sequence variables (existing behavior)
            var sequences = new Dictionary<string, SequenceData>();
            foreach (var (name, value) in _context.CurrentFrame.GetLocalVariables())
            {
                if (value.Data is SequenceData seq)
                {
                    sequences[name] = seq;
                }
            }

            // Add bare expression sequences with auto-generated names
            for (int i = 0; i < bareExpressionSequences.Count; i++)
            {
                // Only add if not already captured as a named variable
                if (!sequences.ContainsValue(bareExpressionSequences[i]))
                {
                    sequences[$"_anon_{i}"] = bareExpressionSequences[i];
                }
            }

            var sectionData = new SectionData(section.Name, sequences, musicalContext, section.Location);
            _context.SectionRegistry[section.Name] = sectionData;
        }
        finally
        {
            _context.PopFrame();
        }
    }
    ```

    Key: The `stmt is ExpressionStatement` check requires importing the AST statement type. Check what namespace it's in (likely `FlowLang.Ast.Statements`) and ensure it's imported. If `ExpressionStatement` is already used elsewhere in Interpreter.cs, the using is already present.

    **FIX-03: Error masking -- ensure function-not-found propagates as failure**

    The research (Pitfall 4) confirms the error path: TryResolveFunction swallows errors -> ResolveFunction reports error -> but Execute() checks HasErrors which DOES include it. So the error IS reported to the ErrorReporter.

    Verify this by tracing: In ExpressionEvaluator.EvaluateFunctionCall (line 186-191), when overload is null, `_context.ResolveFunction(call.Name, argTypes, call.Location)` is called which calls `_errorReporter.ReportError(...)`. Then FlowEngine.Execute returns `!_errorReporter.HasErrors` which will be `false`.

    The actual issue may be that when running via CLI (`dotnet run -e '...'`), the exit code is not set based on Execute() return value. Check Program.cs for how the Execute return value maps to process exit code. If it doesn't, add it.
