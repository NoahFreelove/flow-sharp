    **Polyrhythm implementation (per D-10, D-12):**

    1. Extract both SequenceData from args
    2. Get time signature from first bar of each sequence: `seq.Bars[0].TimeSignature`
    3. Calculate LCM of numerators (per D-10): `Lcm(ts1.Numerator, ts2.Numerator)`
       - `static int Gcd(int a, int b) => b == 0 ? a : Gcd(b, a % b);`
       - `static int Lcm(int a, int b) => a / Gcd(a, b) * b;`
    4. If 3rd arg provided (Int), use that as beat count override (per D-11)
    5. Use a default tempo of 120 BPM and sample rate of 44100 (matching SongRenderer defaults)
    6. Render each sequence independently (per D-12):
       - Calculate total samples needed: `(int)(lcmBeats / (bpm / 60.0) * sampleRate)`
       - For each sequence: render via `SequenceRenderer.RenderSequenceToVoices()`, then loop the output to fill the total duration
       - Looping: if the rendered voice data is shorter than total samples, repeat it (copy samples cyclically)
    7. Mix all voices into a single stereo buffer:
       - Create a float array of `totalSamples * 2` (stereo interleaved)
       - For each voice, add its samples to the buffer (left and right channels)
       - Normalize if any sample exceeds 1.0
    8. Return `Value.Buffer(new AudioBuffer(mixedSamples, sampleRate, 2))`

    **Important:** Check how `AudioBuffer` is constructed -- read the class to understand constructor params (samples array, sample rate, channels). Also check if `SongRenderer.MixVoicesToStereoBuffer` can be made internal/public to reuse, or replicate the mixing pattern.

    If `Voice` class has a `Samples` property (float array) and `Pan` property, iterate voices and apply constant-power panning (same as existing PanningFunctions pattern) during mixing.

    **Variation implementation (per D-13):**

    Core method: `ApplyVariation(SequenceData seq, double probability, string? mutationType, Random rng, string? keyContext)`:
    - Iterate all bars in the sequence (per D-18, create NEW BarData instances, don't mutate)
    - For each note: if `rng.NextDouble() < probability`, apply mutation
    - If `mutationType` is null (per D-15): randomly pick one of "pitch", "rhythm", "rest", "velocity"
    - If `mutationType` is specified (per D-15): apply only that type

    **Four mutation types (per D-13):**

    1. **"pitch"** (per D-17): Shift by 1-2 scale degrees within active key.
       - If keyContext is not null: call `ScaleDatabase.GetScaleNotes(keyContext)`, find current note's position in scale, shift by `rng.Next(-2, 3)` scale degrees, wrap around octave.
       - If keyContext is null: use chromatic movement, shift by `rng.Next(-2, 3)` semitones using MIDI arithmetic (ToMidi/FromMidi pattern from TransformFunctions).
       - Clamp resulting MIDI pitch to range 36-96 (C2-C7).

    2. **"rhythm"**: Split a note into two notes of half duration.
       - Only split if DurationValue allows halving (whole->half=2, half->quarter=4, quarter->eighth=8, eighth->sixteenth=16).
       - The two resulting notes both have the same pitch as the original.
       - Preserve bar total duration (per Pitfall 3 from research).
       - Do NOT merge notes (too complex for v1, splitting only is simpler and avoids duration errors).

    3. **"rest"**: Replace the note with a rest of the same duration.
       - Create `new MusicalNoteData(' ', 0, 0, note.DurationValue, isRest: true, isDotted: note.IsDotted)`

    4. **"velocity"**: Adjust velocity by `rng.NextDouble() * 0.4 - 0.2` (range -0.2 to +0.2).
       - Clamp to [0.05, 1.0].
       - Create new MusicalNoteData with modified velocity.

    **Key context for pitch mutations:** Since built-in functions only receive `IReadOnlyList<Value>` and cannot access `ExecutionContext`, pitch mutations without key context will use chromatic movement (per D-17). Users who want diatonic variation should use the 4-arg overload: `vary(sequence, 0.3, "pitch", "Cmajor")`. Wait -- that conflicts with the seed parameter. Let me reconsider.

    Actually, looking at the overloads defined in D-14 and D-16:

    - `vary(seq, 0.3, "pitch")` -- specific type, no key
    - `vary(seq, 0.3, 42)` -- random mutation, seeded, no key
    - `vary(seq, 0.3, "pitch", 42)` -- specific type, seeded, no key

    For key-awareness: since the registry doesn't support context injection, pitch mutations will use chromatic movement by default. This is acceptable per D-17 ("if no key context, use chromatic movement"). The key-aware path can be a future enhancement if needed. For now, all pitch mutations use +/- 1-2 semitone chromatic movement.
