<interfaces>
Backfill pattern — every `new FunctionSignature(name, types)` call adopts:

```
// BEFORE (existing):
var sig = new FunctionSignature("transpose",
    [SequenceType.Instance, SemitoneType.Instance]);

// AFTER (D-36-11):
var sig = new FunctionSignature("transpose",
    [SequenceType.Instance, SemitoneType.Instance],
    ParameterNames: ["seq", "amount"]);
```

Varargs sites EXEMPT (`IsVarArgs: true`) — per RESEARCH Open Question 2, named args don't apply to varargs. Leave those sites untouched; the resolver short-circuits them per Plan 36-02 Test 10.

Naming convention guidance (composer-facing names — these become the public surface):
- Use the SAME name as the C# lambda's `args[N].As<...>()` variable when one exists
- For Sequence/Buffer/etc. main input: `seq` / `buf` (NOT `s` / `b` — composer-readable)
- For Int counts/indices: `n` / `count` / `index` (use existing convention from the surrounding C# code)
- For arithmetic builtins: `a` / `b` (or `x` / `y` per existing variable naming)
- For lambdas: `fn` / `cb` / `pred`
- For musical args: `note` / `chord` / `tempo` / `degree`

When a builtin has multiple overloads (e.g. transpose has Sequence-Semitone, Sequence-Cent, Sequence-Int forms), the param names should be the SAME across overloads where the parameter semantic is the same — composer's mental model treats them as one logical function.
</interfaces>
