Add `ExecuteForStatement` method. Key details:
- Evaluate the collection expression, get the underlying `List<Value>` (arrays are stored as `List<Value>` in Value.Data)
- For each item: push a new frame, set the loop variable in that frame, execute body statements, pop frame
- Iteration counter is LOCAL to this method call (per Pitfall 2 in RESEARCH.md -- NOT a field on ExecutionContext)
- Check `++iterations > _context.MaxIterations` at start of each iteration; if exceeded, report via `_errorReporter.ReportError()` and break (per D-13)
- Catch `BreakSignal` to break, `ContinueSignal` to continue (per D-04)
- Check `_returnValue != null` after each body statement to propagate returns from inside loops
- Use `finally { _context.PopFrame(); }` to ensure frame cleanup

```csharp
private void ExecuteForStatement(ForStatement stmt)
{
    var collectionValue = _evaluator.Evaluate(stmt.Collection);
    var items = collectionValue.Data as List<Value>;
    if (items == null)
    {
        _errorReporter.ReportError($"Cannot iterate over {collectionValue.Type.Name}; expected an array", stmt.Location);
        return;
    }
    int iterations = 0;
    foreach (var item in items)
    {
        if (++iterations > _context.MaxIterations)
        {
            _errorReporter.ReportError($"Iteration limit of {_context.MaxIterations} exceeded in for loop", stmt.Location);
            break;
        }
        _context.PushFrame();
        try
        {
            _context.CurrentFrame.SetVariable(stmt.VariableName, item);
            foreach (var bodyStmt in stmt.Body)
            {
                ExecuteStatement(bodyStmt);
                if (_returnValue != null) return;
            }
        }
        catch (BreakSignal) { break; }
        catch (ContinueSignal) { continue; }
        finally { _context.PopFrame(); }
    }
}
```

Add `ExecuteWhileStatement` method. Key details:
- Evaluate condition each iteration; verify it's a Bool value (per Pitfall 7 in RESEARCH.md). If non-Bool, report type error and return.
- Same iteration guard pattern as for loop
- Same break/continue/return handling

```csharp
private void ExecuteWhileStatement(WhileStatement stmt)
{
    int iterations = 0;
    while (true)
    {
        if (++iterations > _context.MaxIterations)
        {
            _errorReporter.ReportError($"Iteration limit of {_context.MaxIterations} exceeded in while loop", stmt.Location);
            break;
        }
        var condValue = _evaluator.Evaluate(stmt.Condition);
        if (condValue.Data is not bool condBool)
        {
            _errorReporter.ReportError("While condition must evaluate to Bool", stmt.Location);
            return;
        }
        if (!condBool) break;

        _context.PushFrame();
        try
        {
            foreach (var bodyStmt in stmt.Body)
            {
                ExecuteStatement(bodyStmt);
                if (_returnValue != null) return;
            }
        }
        catch (BreakSignal) { break; }
        catch (ContinueSignal) { continue; }
        finally { _context.PopFrame(); }
    }
}
```

IMPORTANT: Do NOT use `lazy { break }` or `lazy { continue }` inside `if()` calls. The `if` built-in evaluates lazy thunks through `Thunk.Force()` which calls the evaluator, NOT the interpreter's `ExecuteStatement`. This means `BreakSignal`/`ContinueSignal` exceptions thrown from break/continue statements inside lazy blocks will NOT propagate correctly through the `if` function -- they will be swallowed or cause an unhandled exception in the evaluator. Instead, use a `while` loop with a condition flag as a reliable conditional-break pattern.

`tests/test_for_loop.flow`:

```flow
  Bool stop = n == 4
  while stop { break }

// To truly break a for loop conditionally, use a flag + while wrapper:
Int breakSum3 = 0
Bool done = false
Int[] nums3 = [1, 2, 3, 4, 5]

  while idx >= (length nums3) { done = true; break }
  while done { break }
  Int n = nums3@idx
  idx = idx + 1
  Bool shouldStop = n == 4
  while shouldStop { done = true; break }
  breakSum3 = breakSum3 + n
}
(print (str breakSum3))
// Expected: 6 (1+2+3, stops before adding 4)

// Test continue using while-skip pattern
// Skip n==3 by using a while that only runs the add when not skipping
Int contSum = 0
for Int n in [1, 2, 3, 4, 5] {
  Bool shouldSkip = n == 3
  while shouldSkip { continue }
  contSum = contSum + n
}
(print (str contSum))
// Expected: 12 (1+2+4+5, skips 3 -- the while with continue triggers ContinueSignal which propagates to for)

// Test nested for loops
Int product = 0
for Int i in [1, 2, 3] {
  for Int j in [10, 20] {
    product = product + i * j
  }
}
(print (str product))
// Expected: 180 (1*10+1*20+2*10+2*20+3*10+3*20 = 10+20+20+40+30+60 = 180)
```

NOTE on break/continue patterns: `break` and `continue` are statements that throw `BreakSignal`/`ContinueSignal` exceptions. These propagate correctly through the while/for loop's try/catch in the interpreter. The `while shouldSkip { continue }` pattern works because: the `continue` throws `ContinueSignal`, the inner `while` catches it and calls C# `continue` (re-evaluating condition), but `shouldSkip` is still true so it throws again -- BUT the `ContinueSignal` will be caught by the INNER while's catch block, not the outer for. So actually this pattern does NOT work for skipping in the outer loop.

REVISED APPROACH: Since `break`/`continue` only affect the innermost loop, the tests should use them directly in the loop they target. For conditional break/continue, the simplest reliable approach is:
- For `break`: use a `Bool` flag checked at the start of each iteration with `while flag { break }` -- but this only breaks the while, not the for. So instead, just test `break` directly (unconditionally) in loops, and test conditional exit using `while` loops with condition checks.
- For `continue`: same issue -- `continue` in a nested while only continues the while.
