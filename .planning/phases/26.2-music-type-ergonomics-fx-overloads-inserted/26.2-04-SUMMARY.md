### Plan-checker WARNING #3 — Reverb test source escape hatch

The plan flagged that the per-sample-identity test for `reverb(Buffer, Double, Second)` compares `(reverb src 0.5 1.5s)` vs `(reverb src 0.5 1.5)` and provided an escape hatch to revise the test source if `(reverb src 0.5 1.5)` failed to resolve cleanly.

**Resolution:** Escape hatch was unnecessary. The lambda-convergence approach makes per-sample identity hold by construction:

- The new `reverb(Buffer, Double, Second)` C# registration is the ONLY 3-arg reverb overload (the existing 2-arg `ReverbSimple` and 4-arg `ReverbFull` differ in arity).
- Wave-1 `SecondType.IsCompatibleWith(Double)` accepts a bare Double third arg into the Second-typed slot.
- Therefore both `(reverb src 0.5 1.5s)` AND `(reverb src 0.5 1.5)` resolve to the SAME lambda.
- Per-sample identity is guaranteed regardless of the lambda's internal damping/mix formula, because both source forms invoke the identical code path.

The test source was unchanged from Wave-0 scaffolding. The `Reverb_BareDoubleAndSecondVariants_ResolveDistinctlyNoAmbiguity` sentinel passed without modification — both calls resolve cleanly with no overload ambiguity errors in stderr.

## Decisions Made

1. **Music-typed overloads delegate to existing C# lambdas** — Decibel/Millisecond/Hertz CLR backing IS double per `Value.cs:36-39` (Value.Decibel/Millisecond/Hertz factories all wrap a `double`), so `args[i].As<double>()` reads each one directly. No per-overload coercion logic; the closure-captured existing lambda just works. This matches the precedent of Wave-2's `gain(Buffer, Decibel)` registration.

2. **Reverb-Second lambda is NEW (not delegating to ReverbFull)** — Because no existing 3-arg reverb lambda exists (only 2-arg `ReverbSimple` and 4-arg `ReverbFull`), the Second-arm needs its own lambda body. The body uses ReverbSimple-like defaults for damping (derived from decaySec) and mix (0.3f). Both source forms `(reverb buf 0.5 1.5s)` and `(reverb buf 0.5 1.5)` hit this same lambda, guaranteeing per-sample identity.

3. **createSineTone-Hertz needs BOTH C# registration AND Flow-side proc shadow** — The C# `CreateSineTone` lambda produces mono; the existing user-facing Flow proc produces stereo via `createBufferStereo`. To preserve byte-identical behavior with the bare-Double form, the Flow-side proc shadow re-routes user-facing calls through the stereo path. The C# Hertz registration becomes the underlying-primitive surface (callable but shadowed). This design parallels how `createSawTone/createSquareTone/createTriangleTone` work — they're Flow procs only, with no C# registration.

4. **Test source for reverb-Second per-sample-identity unchanged** — Plan-checker WARNING #3 escape hatch was preempted by lambda-convergence: with no other 3-arg reverb overload existing, both Second-typed and bare-Double third-arg calls hit the same lambda regardless of the lambda's internal formula.

5. **NegativeMs assertion split into two specific patterns** — `"Unexpected token"` (lex/parse) + `"No matching overload"` (resolution). The original `"Unexpected"` was over-broad and caught the runtime DSP error wrapper. The test's own comment scopes its contract to lex+resolve, with runtime DSP rejection explicitly allowed.
