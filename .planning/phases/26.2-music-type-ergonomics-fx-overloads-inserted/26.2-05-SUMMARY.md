# Phase 26.2 Plan 05: Wave 4 — `volume(Buffer, Double)` Linear-Multiplier Function Summary

## One-liner

`volume(Buffer, Double)` ships as a function-name-based linear-multiplier alternative to `gain(dB)` — `(volume buf 0.5)` halves amplitude, `(volume buf 2.0)` doubles + emits a stderr clip warning when post-multiplication samples exceed 1.0; negative multipliers rejected with an `InvalidOperationException` mentioning "non-negative"; `(gain buf 0.5)` STAYS as 0.5 dB attenuation per CONTEXT D-07 silent-policy (D-04..D-07 all satisfied; ERG-03 closed). Implementation is a verbatim mirror of `GainEffect` minus the `Math.Pow(10, dB/20)` line plus a `linearMultiplier < 0` reject gate. ## Files Authored / Modified

### `flow-lang/StandardLibrary/Audio/EffectsFunctions.cs` (modified — 1 new C# registration + 1 new lambda body, ~50 LOC)

- **Register dispatch** (line 26): added `RegisterVolume(registry);` after `RegisterSidechain(registry);`.
- **RegisterVolume + VolumeEffect** (appended at end of class, before final `}`): copy-strip of `RegisterGain` + `GainEffect`. The C# lambda:
  1. Reads `linearMultiplier` from `args[1].As<double>()` (Double's CLR backing IS `double` — no conversion needed; same pattern as Decibel/Millisecond/Hertz routing).
  2. Rejects `linearMultiplier < 0` with `throw new InvalidOperationException(...)`. The error-accumulation path surfaces this through stderr (the `errorCount` increments, satisfying `Volume_NegativeMultiplier_Rejected`).
  3. Buffer-empty short-circuit identical to GainEffect.
  4. Per-sample loop: `float sample = buffer.Data[i] * (float)linearMultiplier;` — bare multiplier, no `Math.Pow`. Clip detection `if (Math.Abs(sample) > 1f) wouldClip = true;`.
  5. Warning gate: `if (wouldClip && linearMultiplier > 1.0)` — analogous to GainEffect's `(wouldClip && gainDb > 0)`. Attenuation never clips, so the gate prevents false-positive warnings on `volume(buf, 0.5)`-style calls.
  6. Warning message: `Warning: volume({linearMultiplier:F2}×) causes clipping. Consider reducing volume or applying compression first.` — `:F2` produces `2.00` for `2.0`, satisfying the `Assert.Contains("Warning: volume(2", stderr)` test substring check.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Test bug] `Volume_DoubleMultiplier_DoublesAndEmitsClipWarning` source amplitude bumped 0.5 → 0.8**

- **Found during:** Task 1 (initial test run after removing Skip attribute)
- **Issue:** The test source generated a 0.5-amplitude sine then asserted that `(volume src 2.0)` would emit the clip warning. Verified empirically with a small probe program: `(float)(Math.Sin(2π·phase) * 0.5) * 2.0f` peaks at `0.99999976` (< 1.0 in float precision) — `Math.Abs(sample) > 1f` is never true, `wouldClip` stays false, no warning fires. The plan body's `> 1f` threshold (verbatim from GainEffect) is correct; the test source was unrealistic. Additionally, the per-sample expected used `Math.Clamp(src.Data[i] * 2.0f, -1f, 1f)` — but VolumeEffect mirrors GainEffect and DOES NOT actually clamp/saturate the buffer (it just warns), so the Clamp wrapper would mismatch our impl as soon as values genuinely exceed ±1.
- **Fix:** Bumped source amplitude `0.5 → 0.8` so doubled samples reach ~1.6 (real clipping); dropped the `Math.Clamp(..., -1f, 1f)` wrapper from per-sample expected in favor of bare `src.Data[i] * 2.0f` (matches what VolumeEffect actually stores). Added an inline comment explaining the float-precision rationale and the no-saturate design.
- **Files modified:** `flow-lang.Tests/Unit/Phase26_2/VolumeFunctionFacts.cs`
- **Commit:** `6df301e`

**2. [Rule 2 - Critical functionality / test infrastructure] `[CollectionDefinition("ConsoleCapture", DisableParallelization = true)]` + `[Collection("ConsoleCapture")]`**

- **Found during:** Task 1 (Phase26_2-wide test run — single-class run passed but the warning fact failed inside the parallel run)
- **Issue:** `FlowEngineRunner` (in `flow-lang.Tests/Fixtures/`) uses `Console.SetError(_stderr)` to capture stderr. `Console.SetError` is process-global. When two test classes using FlowEngineRunner run in parallel, the second instance's ctor stomps on the first's redirection — and `Console.Error.WriteLine` from inside `VolumeEffect` ends up writing to a different test's StringWriter (or to nothing if the redirections race). VolumeFunctionFacts is the FIRST test class in the suite that asserts on a runtime-emitted `Console.Error` message; existing stderr-asserting tests (NegativeMusicLiteralFacts, etc.) check ErrorReporter contents flushed via `_stderr.WriteLine(...)` directly inside FlushErrorsToStderr, which bypasses the parallel issue. Result: `Volume_DoubleMultiplier_DoublesAndEmitsClipWarning` failed reproducibly inside the Phase26_2 filter (`stderr == ""`) but passed in isolation.
- **Fix:** Added `[CollectionDefinition("ConsoleCapture", DisableParallelization = true)]` (defined as an empty marker class `ConsoleCaptureCollection`) and applied `[Collection("ConsoleCapture")]` to `VolumeFunctionFacts`. xunit v3 honors the `DisableParallelization = true` flag by serializing this collection against ALL OTHER COLLECTIONS in the assembly — so VolumeFunctionFacts runs alone (no concurrent FlowEngineRunner ctors), and `Console.SetError` redirection is reliable. The rest of the suite remains parallel. With this fix the warning fact is rock-stable across runs.
- **Files modified:** `flow-lang.Tests/Unit/Phase26_2/VolumeFunctionFacts.cs` (added the CollectionDefinition class + the [Collection] attribute on the test class)
- **Commit:** `6df301e`

### Plan-checker WARNING — Test source for clip-warning rounding

The plan body specified `if (Math.Abs(sample) > 1f) wouldClip = true;` (verbatim from GainEffect). The plan also asserted that `Volume_DoubleMultiplier_DoublesAndEmitsClipWarning` MUST flip GREEN as written. These two constraints conflicted because the test as scaffolded used a 0.5-amp sine doubled to 1.0, which never exceeds 1.0 in float arithmetic. Resolution: keep the GainEffect-verbatim `> 1f` threshold (the right policy — the digital ceiling at exactly 1.0 is technically representable as a float sample, no clipping until you exceed it) and adjust the test source upward (Rule 1 deviation #1 above) so that doubling produces genuine clipping. The plan's "shape verbatim" intent referred to the message format and clipping-detection structure, not the exact source values — those belong to the test contract, which is amenable to fixes per the plan's `files_modified` allowance.

## Decisions Made

1. **Function-name-based unit disambiguation** (D-04): `gain` interprets its 2nd arg as decibels, `volume` interprets its 2nd arg as a bare linear multiplier. Composer chooses by semantic intent. Aligns with `feedback_charitable_interpretation` memory: silent-and-documented over magic / educational hints.

2. **Single overload `volume(Buffer, Double)`** (D-05): Float / Int / Long inputs reach it via the existing primitive widening chain (Int → Long → Float → Double). No `volume(Buffer, Float)` separate registration. The `Volume_FloatArgument_WidensToDouble` fact verifies a `Float multF = 0.75; (volume src multF)` call resolves correctly.

3. **GainEffect-mirroring body with symmetric clip gate** (D-06): VolumeEffect copy-strip of GainEffect body — same buffer-empty short-circuit, same per-sample multiply-and-detect-clip loop, same stderr Warning shape. The clip-firing gate is `(wouldClip && linearMultiplier > 1.0)` — analogous to GainEffect's `(wouldClip && gainDb > 0)`. Attenuation (multiplier ≤ 1.0 / dB ≤ 0) never causes clipping, so the symmetric gate prevents false-positive warnings.

4. **Negative volume rejected with explicit message** (D-06): `throw new InvalidOperationException("volume: linear multiplier must be non-negative; received {x}. Use gain(buf, dB) for dB-based attenuation, or a future invertPhase(buf) for phase inversion.");` — surfaces through the engine's error-accumulation path (`errorCount` increments). The "non-negative" / "negative" substring satisfies the test assertion.

5. **No Flow-side convenience wrapper for `volume`** (RESEARCH Open Question #2): matches `gain`'s shape — both go through the C# lambda directly. Adding a Flow proc layer would add nothing and risk inadvertent clamping / scoping differences.

6. **D-07 silent-policy preserved**: NO educational hint when bare-`Double` `gain` is called with arg in `(0, 1)`. `(gain buf 0.5)` is a legitimate 0.5 dB attenuation. The `Gain_BareDoubleSubOne_StillDecibel_RegressionCanary` fact (already GREEN since Wave 0) verifies the dB semantics stay — ratio asserted at `1.0593 ± 0.001` per non-zero sample (the 10^(0.5/20) linear value of +0.5 dB).

7. **Test parallelization carve-out for stderr capture**: Used xunit v3's `[CollectionDefinition(DisableParallelization = true)]` rather than disabling assembly-wide parallelism. Surgical fix that preserves suite throughput while making the runtime-emitted-warning test deterministic. Sets a precedent: any future test class asserting on `Console.Error.WriteLine` from inside the runtime should join the `"ConsoleCapture"` collection.
