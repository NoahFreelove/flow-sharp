# Phase 26.2 Plan 03: Wave 2 — Hz/kHz Lexer Arms + Parser HertzLiteral Routing + audio.flow gain(Decibel) Forward Decl

## One-liner

## Deviations from Plan

### Auto-fixed Issues (Rule 3 — blocking issues)

**1. [Rule 3 - Blocker] TypeParser missing `Hertz` recognition**
- **Found during:** Task 2 — running `Hertz freq = 800Hz` errored with `Unexpected token Assign '=' at line 2:12`
- **Issue:** `TypeParser.ParseType` and `TypeParser.TryParseSingularType` knew about `Decibel`/`Cent`/`Millisecond`/`Second`/`Beat`/`Semitone` but not `Hertz`. Without recognition, `Hertz` parsed as a bare identifier and the assignment failed
- **Fix:** Added `"Hertz" => HertzType.Instance` arms to both methods (lines ~190 and ~303)
- **Files modified:** `flow-lang/Parsing/TypeParser.cs` (not in plan files_modified — Rule 3 added)
- **Commit:** `28158cc`

**2. [Rule 3 - Blocker] Parser.IsTypeKeyword + IsArgumentStart missing `Hertz` / `HertzLiteral`**
- **Found during:** Task 2 (same error as above)
- **Issue:** Even with TypeParser knowing `Hertz`, the Parser dispatch in `IsTypeKeyword` decides whether to call `ParseVariableDeclaration` based on a hardcoded type-name allowlist. `Hertz` was missing from both the singular and plural allowlists. Separately, `IsArgumentStart` excluded `HertzLiteral` so optional-paren-args like `(lowpass src 800Hz)` would have failed
- **Fix:** Added `"Hertz"` to `IsTypeKeyword` (singular, plural-singular check) and `TokenType.HertzLiteral` to `IsArgumentStart`
- **Files modified:** `flow-lang/Parsing/Parser.cs` (this file was in plan files_modified, but the plan only specified the ParsePrimary case — these additional sites are Rule 3 extensions)
- **Commit:** `28158cc`

**3. [Plan-spec mismatch] LiteralExpression signature — followed actual codebase, not plan example**
- **Found during:** Task 2 (reading existing TimeLiteral / DecibelLiteral routing)
- **Issue:** Plan example showed `return new LiteralExpression(HertzType.Instance, (double)hertzToken.Value, hertzToken.Location)` — but `LiteralExpression` is `record (SourceLocation Location, object Value)`. The existing music-literal pattern stores raw text (`PreviousToken.Text`) and `ExpressionEvaluator.TryParseSpecialLiteral` decodes it
- **Fix:** Followed the existing pattern — `LiteralExpression(PreviousToken.Location, PreviousToken.Text)` in Parser; added Hertz arm in `ExpressionEvaluator.TryParseSpecialLiteral` to decode
- **Files modified:** `flow-lang/Interpreter/ExpressionEvaluator.cs` (not in plan files_modified — required because the routing pattern places type-decoding in the evaluator, not the parser)
- **Commit:** `28158cc`

These deviations were necessary for the test acceptance criteria to pass: the canonical fact `Hertz freq = 800Hz` requires recognition at three layers (TypeParser, Parser.IsTypeKeyword, ExpressionEvaluator). The plan correctly identified the lexer + Parser dispatch + audio.flow forward-decl scope but underestimated the type-name surface that needed extension. All deviations follow the same mechanical "add Hertz to the music-type allowlist" pattern that's repeated for every existing music type.

## Decisions Made

1. **kHz-before-Hz ordering enforced in 3 places**: SimpleLexer.ScanNumberOrSpecialLiteral, SimpleLexer.TryLookAheadSpecialLiteral, and ExpressionEvaluator.TryParseSpecialLiteral. Same greedy-match concern in all three — `EndsWith("Hz")` is true for "kHz" strings; longer suffix must be matched first.
2. **Defensive predecessor-set bump for ALL music literals**: TryLexAngleAngle now lists HertzLiteral, TimeLiteral, DecibelLiteral, CentLiteral, SemitoneLiteral. The plan specified just adding HertzLiteral but flagged "if others are missing, add them too." Adding all five is safer (any music-typed value-end can legitimately precede `<<` for a tuple literal); zero regression risk because it's strictly additive.
3. **Raw-text routing for Hertz literals (not type-tagged)**: Followed existing music-literal pattern. The plan example was based on a hypothetical `LiteralExpression(FlowType, object, Location)` constructor that doesn't exist in this codebase. Routing happens in `ExpressionEvaluator.TryParseSpecialLiteral`, mirroring how Decibel / Time / Cent / Semitone literals work.
4. **`gain(Buffer, Decibel)` forward decl placed immediately after `gain(Buffer, Double)` overload**: Same style as how each FX function's overload set is grouped in audio.flow. Two `Note:` lines document the why (ERG-05 ergonomics + RESEARCH Pitfall 2 closure).
5. **Defence-in-depth: dedicated overload + Wave 0 fallback both intact**: After this Wave 2 forward-decl, `(gain src -12dB)` resolves to `gain(Buffer, Decibel)` at exact-match score 1000. The Wave 0 `Value.ConvertTo` Decibel→Double arm is no longer the active fix path but remains as defence-in-depth — if for any reason the Decibel overload is ever removed, the bare-Double overload still works via the coercion path. Both 2 RED-then-Wave-0-GREEN DecibelBeatNumericCompatFacts STAY GREEN.
