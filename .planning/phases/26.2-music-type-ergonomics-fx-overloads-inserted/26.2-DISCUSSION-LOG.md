## Ms/Sec/Semitone compat policy

### Q1 — Should Millisecond and Second gain IsCompatibleWith(Double|Float)?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — symmetric with Cent/Decibel/Beat | Ms.IsCompatibleWith(Double|Float) and Sec.IsCompatibleWith(Double|Float) both ship. Most consistent with the CentType precedent and the 'easy cases fast' goal. | ✓ |
| Yes for Ms only | Sec stays Sec→Ms only. Narrower blast radius but breaks the symmetry. | |
| No — require explicit construction | Composer must write (ms 100) or 100ms; bare Double doesn't reach Ms-typed slots. Preserves type-distinction strictness. | |

**User's choice:** Yes — symmetric.
**Notes:** Mirrors Cent/Decibel/Beat precedent.

### Q2 — How should Millisecond and Second relate to each other?

| Option | Description | Selected |
|--------|-------------|----------|
| Keep CanConvertTo — status quo | Existing CanConvertTo(Ms↔Sec) stays. Sec→Ms-typed slot resolves via convertible-score 100. | ✓ |
| Promote to IsCompatibleWith — exact-match peers | Ms.IsCompatibleWith(Sec) and Sec.IsCompatibleWith(Ms) ship. Risk: overload ambiguity if both Ms and Sec overloads exist for the same FX function. | |
| Drop the cross-conversion entirely | Ms and Sec stop knowing about each other. Loses an existing affordance. | |

**User's choice:** Keep CanConvertTo — status quo.
**Notes:** Existing path is enough; avoids overload-ambiguity risk.

### Q3 — Semitone widening?

| Option | Description | Selected |
|--------|-------------|----------|
| Keep Int-only | Semitone stays as IsCompatibleWith(Int). (transpose seq 2.0) reaches the cent-precision overload, which is the right behavior for fractional pitch shifts. | ✓ |
| Widen to Int|Double|Float | Risk: 2.5 semitones is a legitimate cent-level shift that should arguably go through Cent, not be silently truncated by Semitone. | |

**User's choice:** Keep Int-only.
**Notes:** Fractional pitch shifts go through Cent.

### Q4 — Closure of 2 failing DecibelBeatNumericCompatFacts?

| Option | Description | Selected |
|--------|-------------|----------|
| In scope — close inside 26.2 | STATE.md already says 'Phase 26.2 owns closure'. Tight scope (lexer + maybe parser). | ✓ |
| Split off — separate quick task | Phase 26.2 only handles type-system + overloads. Leaves the 2 failures hanging. | |
| Defer until tutorial/showcase needs it | Don't touch literal forms until Phase 27. Risk: deferred unknowns at milestone close. | |

**User's choice:** In scope.
**Notes:** Aligned with existing STATE.md commitment.

## gain dB-vs-linear policy

### Q1 — gain semantic policy?

| Option | Description | Selected |
|--------|-------------|----------|
| Split: gain=dB-only + ship volume(Buffer, Float) for linear | Two functions, each unambiguous. Aligns with charitable-interpretation memory: silent-and-documented. | ✓ |
| Keep gain only — always dB — document loudly | No new function; CLAUDE.md gets a prominent note. Risk: footgun persists. | |
| Charitable auto-detect by range | Magic, breaks at edge cases, violates 'silent-and-documented' principle. | |
| Rename: existing gain becomes db; ship gain(Buffer, Float) for linear | Most ergonomic but biggest break to existing tutorial.flow / showcase.flow. | |

**User's choice:** Split.
**Notes:** Function name documents the unit.

### Q2 — volume(Buffer, Float) signature shape?

| Option | Description | Selected |
|--------|-------------|----------|
| volume(Buffer, Double) only — widening covers the rest | Single overload. Float/Int auto-widen. Mirrors gain(Buffer, Double) pattern. | ✓ |
| volume(Buffer, Double) + volume(Buffer, Float) overloads | Both registered explicitly. Marginal perf gain; doubles registration code. | |
| volume(Buffer, Number) | Maximum flexibility, but Number specificity is lowest. | |

**User's choice:** volume(Buffer, Double) only.
**Notes:** Simplest path.

### Q3 — volume range / clipping behavior?

| Option | Description | Selected |
|--------|-------------|----------|
| Same clip-warning as gain | Accept any non-negative Double. Stderr Warning when post-multiplication samples exceed 1.0. | ✓ |
| Hard-clamp to [0, 1] | volume is for attenuation only. Safer but surprising. | |
| Accept any value — no warning, no clamp | Trust the composer. Negative phase-invert allowed. | |

**User's choice:** Same clip-warning as gain.
**Notes:** Mirrors existing GainEffect pattern.

### Q4 — Educational hint for bare-Double gain in (0, 1)?

| Option | Description | Selected |
|--------|-------------|----------|
| No hint — silent-and-documented | (gain buf 0.5) is a legitimate 0.5dB attenuation. CLAUDE.md and tutorial.flow document the split. | ✓ |
| One-time hint when arg is in (0, 1) | First call per session prints a hint. Risk: non-determinism, potential byte-identical determinism leak. | |
| Warn always when arg is in (0, 1) | Spammy, false-positive heavy. | |

**User's choice:** No hint.
**Notes:** Charitable-interpretation memory's silent-and-documented lean.

## FX overload coverage scope

### Q1 — Which FX functions get Millisecond overloads?

| Option | Description | Selected |
|--------|-------------|----------|
| delay(Buffer, Millisecond, Double, Double) | Coexists with NoteValue-rate overload from DX-12. | ✓ |
| compress(Buffer, Double, Double, Millisecond, Millisecond) | Threshold + ratio stay Double. | ✓ |
| sidechain(Buffer, Buffer, Double, Double, Millisecond, Millisecond) | Same shape as compress. | ✓ |
| reverb(Buffer, Double, Second) for decay-time | Verify it doesn't ambiguate the simple (reverb buf mix) form. | ✓ |

**User's choice:** All four.
**Notes:** Music-type overloads land on every conceptually-natural site.

### Q3 — Combinatorial overload coverage?

### Q4 — Test pattern?

## Hertz type (ERG-04)

### Q1 — Hertz scope?

| Option | Description | Selected |
|--------|-------------|----------|
| Ship in 26.2 — same shape as Decibel | Small marginal cost given we're already in the FX overload domain. Phase 27 gets a complete music-type story. | ✓ |
| Split into Phase 26.3 | Smaller 26.2 blast radius. Risk: tutorial.flow refresh in Phase 27 lands without Hertz. | |
| Defer to v1.4 entirely | Composer writes 800.0 not 800Hz. Defers a pure-ergonomics gain. | |

**User's choice:** Ship in 26.2.
**Notes:** Complete music-type story for Phase 27 tutorial.

### Q2 — Hz / kHz suffix support?

| Option | Description | Selected |
|--------|-------------|----------|
| Both Hz and kHz | Lexer produces a single HertzLiteral token from 800Hz and 1.5kHz alike; kHz multiplied at lex time. | ✓ |
| Hz only | Composer writes the multiplication explicitly. Less ergonomic for high cutoffs. | |
| Hz, kHz, AND mHz | mHz = milli-Hertz for slow modulation. No FX builtin needs it; LFOs aren't in the language yet. | |

**User's choice:** Both Hz and kHz.
**Notes:** Reads ergonomically across the audible range (20Hz–20kHz).

### Q3 — Hertz overload coverage?

| Option | Description | Selected |
|--------|-------------|----------|
| Filters + signal generators | lowpass/highpass/bandpass + sine/saw/square/triangle. | |
| Filters only | Smallest 26.2 footprint. | |
| Filters + signal generators + setNyquist (PitchConversion) | Covers every Hz-typed parameter site in flow-lang. | ✓ |

**User's choice:** Filters + signal generators + PitchConversion APIs.
**Notes:** Maximum surface — every Hz-typed Double param gets a Hertz overload.

### Q4 — Hertz IsCompatibleWith?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — IsCompatibleWith(Double|Float) | Bare-Double overload wins via exact-match (1000); Hertz literal hits the new overload directly. | ✓ |
| No — Hertz is its own type only | Composer must use Hz literals. Clean separation but breaks the established pattern. | |

**User's choice:** Yes.
**Notes:** Same shape as the rest of the music-type family.
