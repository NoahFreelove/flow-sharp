# Phase 26.2: Music Type Ergonomics + FX Overloads — Research

**Researched:** 2026-05-10
**Domain:** Flow language type system + audio FX builtin registration + lexer literal coverage
**Confidence:** HIGH (root cause of failing facts traced to a missing `internal proc gain(Buffer, Decibel)` in audio.flow + a missing `targetType is DoubleType` clause in `Value.ConvertTo`; everything else verified via code reading + actual test-run reproduction)

## Summary

Phase 26.2 makes the music-type family (Decibel, Beat, Cent, Semitone, Millisecond, Second + new Hertz) first-class at every audio FX call site. ROADMAP entry overstates the gap — Decibel/Beat IsCompatibleWith and the `gain(Buffer, Decibel)` C# registration shipped in QUICK-260504-w24 (commit 1960a92). The 2 pre-existing failing `DecibelBeatNumericCompatFacts` are NOT a lexer/parser bug as the test comment hypothesizes — the lexer correctly produces a `DecibelLiteral` token from `+6dB`/`-12dB` at expression-start, and the OverloadResolver scoring is correct. The actual root cause is a **forward-declaration gap**: `audio.flow` has no `internal proc gain(Buffer: b, Decibel: d)` line, so the C# `gain(Buffer, Decibel)` registration never enters the user-visible overload set; the bare-`gain(Buffer, Double)` wins via `Decibel.IsCompatibleWith(Double)`, then `Value.ConvertTo(DoubleType)` crashes on a Decibel-typed double because the `Data is double` branch in `Value.cs:155-161` lacks a `targetType is DoubleType` clause.

The fix matrix is mechanical and additive. Six existing music types each get a one-line `IsCompatibleWith(Double|Float)` (Ms/Sec only — Decibel/Beat/Cent already shipped; Semitone STAYS Int per D-03). Each new music-type FX overload requires three coordinated edits: a C# `registry.Register(...)` line in `EffectsFunctions.cs`, a matching `internal proc <name>(... <MusicType>: arg)` line in `audio.flow`, and a `Value.ConvertTo` patch (one line per missing target arm in the `Data is double` chain). New `HertzType` mirrors `CentType` exactly. New `volume(Buffer, Double)` builtin copies `GainEffect` body verbatim minus the `Math.Pow(10, dB/20)` line.

**Primary recommendation:** Wave 0 establishes the test scaffolding + the `Value.ConvertTo` D→D/F→F clause repair (this single edit makes the 2 failing facts GREEN as a side-effect by fixing the `Decibel→Double` coercion path even if the dedicated Decibel overload never gets surfaced). Wave 1 lands the type-system additions. Wave 2 lands the lexer Hz/kHz literal paths + audio.flow forward declarations for the existing-but-not-surfaced `gain(Buffer, Decibel)` overload. Wave 3 lands all FX overloads in parallel (additive registrations — no shared mutable state). Wave 4 ships `volume`. Wave 5 closes phase with REQUIREMENTS.md authoring + CLAUDE.md updates.

### Pattern 3: Hz/kHz literal lexing (mirror existing dB suffix paths)
**What:** Lex `800Hz` and `1.5kHz` as a single `HertzLiteral` token whose Value is a canonical Hz double (kHz × 1000).
**When to use:** D-11 + D-12.
**Example (mirror SimpleLexer.cs:579-590 dB pattern in 3 places):**

The lexer has THREE places that handle suffix-detection — all three need parallel Hz/kHz paths:

1. `TryLookAheadSpecialLiteral` (lines 508-627) — handles `+/-N<suffix>` at expression-start. Add Hz + kHz arms.
2. `ScanNumberOrSpecialLiteral` (lines 629-733) — handles unsigned `N<suffix>` (e.g. `800Hz`, `0dB`). Add Hz + kHz arms.
3. `ScanIdentifierOrKeyword` paths via `TryParseDecibel`/`TryParseTime` etc. (lines 988-1031) — for the case where a number-letter run got absorbed into an identifier. Add `TryParseHertz` helper.

**CRITICAL ordering:** `kHz` (3 chars) MUST be checked BEFORE `Hz` (2 chars). Reason: lexer reads forward; if `Hz` is checked first against the `H` of `kHz`, the `k` may be consumed as identifier and `Hz` lexes alone. Mirrors the existing `s`-vs-`ms`-vs-`st` ordering precedent — the lexer carefully distinguishes `1.5s` from `1.5ms` from `1st` via PeekNext checks (see SecondType.Parse rejection comment line 28: `secStr.EndsWith("ms")` exclusion). Same kind of disambiguation applies to `kHz`-before-`Hz`.

**However:** because `Hz` ALWAYS appears after a digit and `k` is not a valid Flow keyword/identifier-start in this position, the practical safe order is "match `kHz` only if the previous-emitted-char run is a digit; otherwise match plain `Hz`". The existing dB pattern handles this naturally because `dB` is `d`+`B` and `d` is not a Flow keyword either. For Hz/kHz the cleanest approach is:

```csharp
// In ScanNumberOrSpecialLiteral, AFTER number-text scan:
// Try "kHz" suffix FIRST (3-char), then "Hz" (2-char)

    if (double.TryParse(numberText, out double kHzValue))

}
else if (Peek() == 'H' && PeekNext() == 'z')
{
    Advance(); Advance();  // consume Hz
    if (double.TryParse(numberText, out double HzValue))
        return new Token(TokenType.HertzLiteral, sb.ToString(), start, HzValue);
}
```

// Source: copy of EffectsFunctions.GainEffect (lines 305-332)
private static Value VolumeEffect(IReadOnlyList<Value> args)
{
    var buffer = args[0].As<AudioBuffer>();
    double linearMultiplier = args[1].As<double>();

    // D-06: reject negative volume (would phase-invert; use a separate function for that)
    if (linearMultiplier < 0)
        throw new InvalidOperationException("volume: linear multiplier must be non-negative; received " + linearMultiplier);

    if (buffer.Frames == 0)
        return Value.Buffer(new AudioBuffer(0, buffer.Channels, buffer.SampleRate));

    var result = new AudioBuffer(buffer.Frames, buffer.Channels, buffer.SampleRate);

    bool wouldClip = false;
    for (int i = 0; i < buffer.Data.Length; i++)
    {
        float sample = buffer.Data[i] * (float)linearMultiplier;
        if (Math.Abs(sample) > 1f) wouldClip = true;
        result.Data[i] = sample;
    }

    // D-06: only warn when the result actually clips (mirrors GainEffect)
    if (wouldClip)
    {
        Console.Error.WriteLine(
            $"Warning: volume({linearMultiplier}×) causes clipping. Consider reducing volume or applying compression first.");
    }

    return Value.Buffer(result);
}

### Anti-Patterns to Avoid

- **DON'T** register a C# overload without adding the matching `internal proc` line in audio.flow. The C# registration without the forward-decl is dead code — the overload never enters the user-visible resolution set. **This is exactly why the 2 currently-failing facts fail.**
- **DON'T** patch `Value.ConvertTo` for music-type → Double in a way that drops information. The current conversion error is a symptom of two separate gaps; fix both rather than masking one.
- **DON'T** rename existing `gain(Buffer, Double)` or `createSineTone(Double, Double, Double)` — D-04 explicitly chose function-name-based split (`gain` vs `volume`) over rename, and D-13 explicitly says "bare-Double overloads NOT removed, only joined."
- **DON'T** modify `examples/tutorial.flow` or `examples/showcase.flow` — Phase 27 owns those (CONTEXT § Specifics last bullet, D-16 byte-identical contract).
- **DON'T** add `mHz` (millihertz) lexing — explicitly out of scope per CONTEXT § Deferred Ideas.
- **DON'T** widen `Semitone.IsCompatibleWith(Double|Float)` — D-03 explicitly keeps Semitone Int-only so `(transpose seq 2.0)` continues to reach `transpose(Sequence, Cent)` (existing precedent). Widening Semitone would create ambiguity at every transpose call.

## Common Pitfalls

### Pitfall 1: The `Data is double` ConvertTo gap
**What goes wrong:** `Value.ConvertTo(targetType=Double)` on a Decibel-typed Value (Data=double) throws `InvalidCastException` despite both having underlying CLR type `double`. This causes the `(gain src -12dB)` engine-eval test to fail with "Cannot convert Flow type 'Decibel' with underlying CLR type 'Double' to Flow target type 'Double'". [VERIFIED: reproduced via test run on 2026-05-10; error message exactly matches Value.cs:252.]
**Why it happens:** `Value.cs:155-161` `if (Data is double doubleVal)` chain handles IntType/LongType/FloatType/NumberType target arms but lacks `if (targetType is DoubleType) return Double(doubleVal);`. Since base `FlowType.CanConvertTo` defaults to `IsCompatibleWith` (FlowType.cs:24-27) and Decibel.IsCompatibleWith(Double) returns true, the coercion call at `ExpressionEvaluator.cs:249` fires; ConvertTo then throws because no arm catches it.
**How to avoid:** Add the missing arm:
```csharp
// In Value.cs:155 if-branch, add as the first arm:
if (Data is double doubleVal)
{
    if (targetType is DoubleType) return Double(doubleVal);   // NEW — defence-in-depth
    if (targetType is IntType) return Int((int)doubleVal);    // existing
    ...
}
```
**Warning signs:** Any `(builtin musicTypedVar)` engine-eval that passes a music-type value to a Double-typed parameter slot will throw the InvalidCastException. The error message uniquely identifies the bug (target type's name will match the source's underlying CLR type's name).

### Pitfall 2: The audio.flow forward-declaration gap
**What goes wrong:** A C# `registry.Register("gain", Buffer/Decibel-sig, lambda)` line ships, but `(gain src -12dB)` resolves to `gain(Buffer, Double)` (the bare-Double overload) instead of the dedicated Decibel overload. The Decibel overload's score (2000) would beat the bare-Double overload's score (1500), but the resolver never sees the Decibel overload as a candidate.
**Why it happens:** `Interpreter.ExecuteProcDeclaration` (Interpreter.cs:457-471) only declares an overload into the user-visible scope when an `internal proc` declaration matches a registered C# implementation. If audio.flow has only `internal proc gain(Buffer: b, Double: dB)` and not `internal proc gain(Buffer: b, Decibel: dB)`, then only the Double overload reaches `_context.DeclareFunction`. The C# Decibel registration in `EffectsFunctions.cs:296-298` is dead code.
**How to avoid:** Every C# `registry.Register("name", sig, lambda)` MUST have a matching `internal proc name(<sig>)` line in the corresponding `.flow` standard-library module (audio.flow for FX, std.flow for transforms, collections.flow for collections, etc.). Verify by grep:
```bash
# After adding gain(Buffer, Decibel) C# registration, verify:
grep -n "internal proc gain" flow-lang/audio.flow
# Should list BOTH (Buffer, Double) AND (Buffer, Decibel)
```
**Warning signs:** The OverloadResolver picks an overload one would not expect, AND the chosen overload has a lower-scored type-compat path that exercises Pitfall 1's Value.ConvertTo bug.

### Pitfall 3: Reverb arity-vs-Second ambiguity (CONTEXT D-08 sentinel)
**What goes wrong:** Adding `reverb(Buffer, Double, Second)` could ambiguate with the existing `reverb(Buffer, Double, Double)` for the call `(reverb buf 0.5 1.5)` (no `s` suffix on the third arg).
**Why it happens:** After D-01 lands, `Second.IsCompatibleWith(Double|Float)` is TRUE. So `(reverb buf 0.5 1.5)` with argTypes `[Buffer, Double, Double]` matches:
- `reverb(Buffer, Double, Double)`: 1000 + 1000 + 1000 = **3000** (all exact)
- `reverb(Buffer, Double, Second)`: 1000 + 1000 + 500 (Double→Second compat via reverse-IsCompatibleWith) = **2500**

Bare-Double overload wins by 500 points. NOT ambiguous; CONTEXT D-08 sentinel passes.

For the Second-typed call `(reverb buf 0.5 1.5s)` with argTypes `[Buffer, Double, Second]`:
- `reverb(Buffer, Double, Double)`: 1000 + 1000 + 500 (Second→Double compat) = **2500**
- `reverb(Buffer, Double, Second)`: 1000 + 1000 + 1000 = **3000**

Second overload wins by 500 points. Correct dispatch.
**How to avoid:** Add a unit test asserting both calls resolve unambiguously. Pattern:
```csharp
[Fact]

{
    using var runner = new FlowEngineRunner();
    var (_, _, stderr, errorCount) = runner.RunSource(@"
use ""@std""
use ""@audio""

        Assert.True(MathF.Abs(rd.Data[i] - rs.Data[i]) < 1e-6f);
}
```
**Warning signs:** "Ambiguous overload for function 'reverb'" in stderr.

### Pitfall 4: Hz/kHz lexing order — lexer rewind risk
**What goes wrong:** Lexing `1.5kHz` could produce `IntLiteral(1)` `Dot` `IntLiteral(5)` `Identifier(kHz)` if the lexer doesn't extend its number-then-suffix scan to include `kHz` in addition to existing `dB`/`ms`/`s`/`c`.
**Why it happens:** `ScanNumberOrSpecialLiteral` (lines 629-733) has explicit `if/else if` arms for each known suffix. Hz/kHz is a NEW suffix family; without an arm, the lexer falls back to "regular number" and the `kHz` identifier-start chars become a separate identifier token.
**How to avoid:** Add Hz/kHz arms to BOTH `ScanNumberOrSpecialLiteral` (unsigned path) and `TryLookAheadSpecialLiteral` (signed-prefix path), matching the existing dB/ms pattern. Order check: `kHz` arm BEFORE `Hz` arm.
**Warning signs:** A test like `Hertz x = 1.5kHz` errors with "Unexpected identifier 'kHz'" or fails to parse. Or `Hertz x = 800Hz` errors with "Unexpected identifier 'Hz'".

### Pitfall 5: Byte-identical regression via OverloadResolver tie
**What goes wrong:** Adding new music-type overloads changes the candidate count for FX function calls. If two overloads tie on specificity score, the OverloadResolver throws `Ambiguous overload`, which can break previously-working `tutorial.flow` / `showcase.flow` calls.
**Why it happens:** `OverloadResolver.cs:72-79` rejects ties explicitly. New overloads register at exact-match (1000) for music-typed args. As long as the bare-Double overload also exists at exact-match for Double-typed args, the score gap is 1500 vs 2000 (or 2500 vs 3000 for 3-arg calls) — never a tie.
**How to avoid:**
- D-09: each FX function gets exactly ONE new music-typed overload (NOT a 2^N combinatorial set).
- The new overload's arity matches an existing arity AND the music-type-position differs from the bare-Double overload's type at the same position.
- Verify by running `Phase18 ByteIdenticalShowcaseTests` + `Phase25 ByteIdenticalShowcaseGaussianTests` after every wave commit.
**Warning signs:** "Ambiguous overload for function 'X'" in showcase.flow or tutorial.flow output during build/test.

### Pitfall 6: Forgetting to bump Hertz token for `<<`/`>>` predecessor set
**What goes wrong:** After adding `HertzLiteral` token type, an expression like `<<800Hz, 440Hz>>` could fail to parse if `HertzLiteral` is not in the `TryLexAngleAngle` expression-start predecessor set.
**Why it happens:** `SimpleLexer.cs:411-429` lists token types that are valid predecessors for `<<` (a tuple literal can follow them). The list explicitly enumerates `IntLiteral`, `FloatLiteral`, `StringLiteral`, `BoolLiteral`, `NoteLiteral`, `ChordLiteral`, `SymbolLiteral`, `LessLess`, `GreaterGreater`. New literal types (e.g. HertzLiteral) need to be added.
**How to avoid:** When introducing `HertzLiteral`, also add it to the `TryLexAngleAngle` `isExprStart` predecessor set. Test:
```flow
Tuple<<Hertz, Hertz>> band = <<800Hz, 1200Hz>>
```
This should parse — if it fails with a `<<` lex error, the predecessor set is missing HertzLiteral.
**Warning signs:** Tuple literals containing Hz values fail to parse with a `<<`-related lex error.

namespace FlowLang.TypeSystem.SpecialTypes;

public sealed class HertzType : FlowType
{
    private HertzType() { }
    public static HertzType Instance { get; } = new();
    public override string Name => "Hertz";
    public override int GetSpecificity() => 144;  // one above Cent (143) — must be unique
    public override bool IsCompatibleWith(FlowType target)
    {
        return target is DoubleType or FloatType || base.IsCompatibleWith(target);
    }
    public static double Parse(string hzStr)
    {
        // "800Hz" -> 800.0;  "1.5kHz" -> 1500.0
        if (hzStr.EndsWith("kHz"))
        {
            string n = hzStr[..^3];
            return double.Parse(n) * 1000.0;
        }
        if (hzStr.EndsWith("Hz"))
            return double.Parse(hzStr[..^2]);
        throw new ArgumentException($"Invalid hertz format: {hzStr}");
    }
}

## Security Domain

> Per the project's "ergonomics-first, music-only scope" memory, security is not a primary concern for this phase. The phase introduces no network I/O, no file I/O beyond existing WAV/MIDI write paths, no user-input parsing of untrusted data, no auth/session/access-control surfaces. The single applicable category is V5 Input Validation.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | — (no auth surfaces) |
| V3 Session Management | no | — |
| V4 Access Control | no | — |
| V5 Input Validation | yes | Native C# `double.TryParse` for lexer literal parsing; explicit range rejection in `volume` (D-06: negative rejected; clipping warning on result > 1.0). |
| V6 Cryptography | no | — |

### Known Threat Patterns for Flow language interpreter

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Lexer DoS via degenerate signed-suffix input (e.g. `-12345...kHz` with millions of digits causing infinite loop) | DoS | The lexer's number-scan loop terminates at first non-digit — bounded by source length. Suffix matching is constant-time (PeekNext()). Mitigation: existing — no new threat introduced. |
| Volume(Buffer, Double) integer overflow when result samples exceed float range | Tampering | `float sample = buffer.Data[i] * (float)linearMultiplier` will saturate to `+/-Inf` for absurd multipliers; the clipping warning fires if any abs-sample > 1.0. Mitigation: D-06 clipping warning is explicit. |
| Negative `volume` causing phase-invert injection (a composer expects scaling, gets phase-flip) | Tampering | D-06: rejected with `InvalidOperationException`. Phase-invert intentionally NOT supported on `volume`. |
| Hertz `Parse("kHz" + "very-large-number")` overflow | DoS | `double.TryParse` returns false on overflow; the lexer reports a parse error rather than producing a `+/-Inf` token. Mitigation: existing path. |
