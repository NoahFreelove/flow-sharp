<objective>
Produce decisive evidence for audit claim **C3** ("EnvelopeProcessor div-by-zero on sub-frame durations at lines 108, 120, 150, 156, 169") per SPIKE-03.

The architecture researcher argues the `for (int i = 0; i < attackFrames; i++)` loop is gated on `attackFrames >= 1`, so divisions like `(float)i / attackFrames` at line 108 only execute when the denominator is nonzero. The pitfalls researcher argues that at low sample rates with short attack times, `attackFrames` can be 0 but the loop body never runs, so it's the wrong kind of bug — the actual risk is sample-rate-dependent silent clipping from Math.Max workarounds. Only hypothesis A (real div-by-zero) would produce a crash; if there's no crash, the dismissal stands.

**Purpose:** Settle whether C3 reproduces as a crash from Flow user code.
**Output:** `tests/spike/c3-envelope-short-segments.flow` + a single inline `// AUDIT-VERIFIED 2026-04-18: C3 — <verdict>` in EnvelopeProcessor.cs near line 108.

**D-05 fallback:** If `createAR`/`createADSR`/`applyEnvelope` cannot be invoked from user `.flow` code with a controllable sample rate (i.e., the buggy path is internal-only), this plan records a reasoning-only dismissal in the inline comment and notes in SUMMARY that no positive test was feasible. The investigation still runs — just produces a text verdict rather than a script.
</objective>
